## 提案 P-002a — 抽象角色 → 13 角色包绑定表

- **问题**：P-001 的 §2.4.5 协调官闭环中，Planner/Dispatcher/Executor/Verifier 到具体 `role-*` 包的映射靠人肉判断（见 P-001 dry-run 样例）；`team-orchestration/domain/dependency-graph.md` 的 `TaskNode.role` 用抽象名（architect/executor/test-engineer/writer），**未绑定 13 个具体角色包**，诉求 #2 成熟度仅 3.5/5。
- **根因**：team-orchestration 是通用并行层，设计上与具体角色包解耦；缺一张"抽象角色×任务类型→角色包"的解析表把两者接起来。
- **改进方案**：在 `team-orchestration/domain/dependency-graph.md` 新增 §6「抽象角色 → 13 角色包绑定表」+ `resolve_role(abstract_role, task_type)` 解析函数，Dispatcher 阶段查表分派；`team-orchestration` SKILL.md §3.1 加引用。
- **预期收益**：诉求 #2 从 3.5→4.5；协调官闭环的"指派"从人肉变可查表，DAG 每个 TaskNode 落到确定角色包。
- **成本**：低（1 个 domain 新增小节 + 子技能版本号；无新角色、无新工具）。
- **风险**：低。绑定表是数据/查表，不改执行逻辑；任务类型判定沿用编排器 §2.4.2 映射表（单一信息源，不重复定义）。
- **评估方式**：版本/闭环门禁全绿；绑定表覆盖 13 角色 + 5 抽象角色；四目录部署 grep。
- **回退**：删 §6 小节 + 版本回退，git revert。
- **优先级**：P1。

## 提案 P-002b — 交互自动收割（确认清单模板复用）

- **问题**：诉求 #6「多次必要交互→形成经验→以后可参考」成熟度仅 3/5。self-improve 有经验采集(§4.2)+create_memory 集成，但**无"同类任务确认交互≥N轮→自动抽取确认清单模板→沉淀→下次提前复用"的触发器**，确认经验靠人工记忆。
- **根因**：铁律#10 六段合同管"单次提前确认"，铁律#13 SGD 管"减少交互"，但两者都不负责"把重复出现的确认问答跨会话沉淀为可复用模板"。
- **改进方案**：新建 `self-improve/domain/interaction-harvest.md`，定义闭环：触发（同类任务确认≥N轮，默认N=3，或同一澄清问题重复≥2次）→ 抽取 Q&A 生成「确认清单模板」→ 沉淀到外部 Memory（`create_memory` MCP，category=skill_experience）+ 可选 `台账/23_复用资产.csv` → 下次同类任务 Planner 阶段先检索命中模板，提前一次性确认（复用铁律#10）、减少交互（复用铁律#13）。`self-improve` SKILL.md §3.2 加引用。
- **预期收益**：诉求 #6 从 3→4.5；重复确认经验跨会话可复用，交互次数随经验积累递减。
- **成本**：低（1 个新 domain + 子技能版本号；sink 复用现有 create_memory MCP，不新建工具）。
- **风险**：低。收割是加法式，不改现有确认流程；模板命中失败则回退到铁律#10 常规确认。
- **评估方式**：版本/闭环门禁全绿；闭环三要素齐（工具承载=create_memory MCP / 台账承载=23_复用资产.csv可选 / 触发=交互计数器）；四目录部署 grep。
- **回退**：删 interaction-harvest.md + 版本回退，git revert。
- **优先级**：P1。
