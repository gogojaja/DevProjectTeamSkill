# 文档评审流程优化方案

> **文档编号**：OPT-REVIEW-001
> **编制日期**：2026-09-07
> **编制人**：段波
> **适用范围**：Excel/Word 需求文档评审全流程（读取→评审→修复→验证→台账同步）
> **依据**：测试管理需求 V1.2.1 评审实战经验

---

## 一、背景与问题分析

### 1.1 现状

本项目在测试管理需求 V1.2 → V1.2.1 的评审过程中，完整执行了以下流程：

```
读取 xlsx → 逐工作表人工对比 → 生成缺陷清单 → 输出评审报告 CSV
→ 更新质量缺陷台账 → 编写修复脚本 → 执行修复 → 人工验证 → 更新台账状态
```

### 1.2 痛点清单

| # | 痛点 | 影响 | 根因 |
|:---:|------|------|------|
| P1 | PowerShell 中文输出编码问题 | xlsx 内容无法直接通过 Shell 输出，必须先写入 txt 再读取 | Windows PowerShell 5 默认编码不兼容 UTF-8 |
| P2 | 评审报告手工拼接 | 每次评审需手写 CSV 内容，格式不统一 | 无评审报告生成器 |
| P3 | 修复脚本一次性硬编码 | 修复指令与路径写死在脚本中，不可复用 | 无指令驱动的批量修复工具 |
| P4 | 验证全靠人工读文件 | 修复后需重新导出全表内容逐条核对 | 无自动化验证工具 |
| P5 | 台账更新靠手工编辑 | 每次 SearchReplace 编辑台账，易出错 | 无台账同步工具 |
| P6 | 三向一致性检查靠人工 | 界面设计 vs 表单 vs 业务规则需逐行交叉对比 | 无一致性检查引擎 |
| P7 | Word 文档评审无前置工具 | 无法快速提取 docx 结构 | 未实现 docx 结构提取器 |

### 1.3 已验证的有效模式

本会话验证了以下可复用模式：

- **xlsx → txt 导出**：通过 openpyxl 读取后写入 UTF-8 文件，绕过 PowerShell 编码问题（已验证可行）
- **缺陷清单 CSV 格式**：`缺陷编号,严重级别,功能模块,缺陷类型,缺陷描述,界面设计依据,表单/规则依据,建议修复方案,提出人,提出日期`（已验证格式合理）
- **逐维度评分 CSV 格式**：`评审维度,权重,得分,评审结论,主要问题说明`（已验证可输出）
- **修复指令化**：修复脚本按缺陷编号逐条执行（已验证逻辑清晰，但需抽象为指令驱动）

## 二、目标

### 2.1 总体目标

将文档评审从「人工逐行对比 + 手工拼接报告 + 一次性修复脚本」升级为「工具链自动化 + 规则驱动 + 流程闭环」。

### 2.2 量化指标

| 指标 | 当前 | 目标 | 改善幅度 |
|------|:---:|:---:|:---:|
| 评审准备时间（读取+对比） | ~15 min | ~2 min | 87% ↓ |
| 评审报告生成时间 | ~10 min | ~10 s | 98% ↓ |
| 修复脚本编写时间 | ~20 min | ~3 min（仅写指令） | 85% ↓ |
| 修复验证时间 | ~10 min | ~30 s | 95% ↓ |
| 台账更新时间 | ~5 min | ~5 s | 98% ↓ |
| 评审全流程总耗时 | ~60 min | ~10 min | 83% ↓ |

## 三、方案设计

### 3.1 工具清单（7 个独立脚本工具）

#### T-01：xlsx_dump —— Excel 全量导出器

| 项 | 内容 |
|---|------|
| **输入** | `--input <xlsx路径>` `--output <输出路径>` `--format txt\|json` |
| **输出** | 全工作表内容（含单元格坐标、值、合并单元格信息） |
| **核心逻辑** | openpyxl load → 遍历 sheet → 提取 cell.value → 写入 UTF-8 文件 |
| **解决痛点** | P1（PowerShell 编码问题） |
| **依赖** | openpyxl |
| **预估开发** | 0.5 人时 |

#### T-02：xlsx_diff —— Excel 版本对比器

| 项 | 内容 |
|---|------|
| **输入** | `--old <旧版xlsx>` `--new <新版xlsx>` `--output <差异报告路径>` |
| **输出** | 差异清单：`工作表,单元格,旧值,新值,变更类型(新增/修改/删除)` |
| **核心逻辑** | 双 xlsx dump → 逐工作表逐单元格比对 → 输出 diff |
| **解决痛点** | P6（版本对比靠人工） |
| **依赖** | T-01 |
| **预估开发** | 1 人时 |

#### T-03：review_report_gen —— 评审报告生成器

| 项 | 内容 |
|---|------|
| **输入** | `--defects <缺陷清单JSON>` `--output <输出目录>` `--object <评审对象>` `--version <版本号>` |
| **输出** | 两份 CSV：`评审报告_<对象>_<版本>_缺陷.csv` + `评审报告_<对象>_<版本>_逐维度.csv` |
| **核心逻辑** | 读取缺陷 JSON → 按严重级别统计 → 逐维度评分计算 → 输出标准 CSV（UTF-8 BOM） |
| **解决痛点** | P2（报告手工拼接） |
| **依赖** | 无 |
| **预估开发** | 1 人时 |

#### T-04：defect_ledger_sync —— 缺陷台账同步器

| 项 | 内容 |
|---|------|
| **输入** | `--defects <缺陷清单JSON>` `--ledger <台账路径>` `--round <评审轮次>` `--status <状态>` |
| **输出** | 台账文件追加/更新评审记录 |
| **核心逻辑** | 解析台账格式（md/csv 适配器）→ 追加评审轮次表 → 按缺陷编号更新状态 |
| **解决痛点** | P5（台账手工编辑） |
| **依赖** | 无 |
| **预估开发** | 1.5 人时 |
| **备注** | 需支持 .md 台账（本项目）和 .csv 台账（其他项目）两种格式 |

#### T-05：xlsx_cell_fix —— Excel 批量修复器

| 项 | 内容 |
|---|------|
| **输入** | `--input <xlsx路径>` `--fixes <修复指令JSON>` `--output <输出路径>` |
| **修复指令格式** | `[{"id":"DEF-001","cells":[{"ref":"D21","value":"计算后回显"}],"sheet":"表单-当日测试情况"}]` |
| **输出** | 修复后 xlsx + 修复执行日志（JSON） |
| **核心逻辑** | 读取修复指令 → 逐条定位 sheet+cell → 写入新值 → 保存 xlsx → 输出日志 |
| **解决痛点** | P3（修复脚本一次性硬编码） |
| **依赖** | openpyxl |
| **预估开发** | 1.5 人时 |
| **备注** | 修复指令 JSON 可版本化、可审计，替代当前一次性 Python 脚本 |

#### T-06：xlsx_verify —— Excel 修复验证器

| 项 | 内容 |
|---|------|
| **输入** | `--input <修复后xlsx>` `--defects <缺陷清单JSON>` `--output <验证报告路径>` |
| **输出** | 验证矩阵：`缺陷编号,验证结果(已修复/未修复/部分修复),实际值,预期值,备注` |
| **核心逻辑** | 读取缺陷清单 → 逐条定位修复目标单元格 → 比对实际值与预期值 → 输出验证结果 |
| **解决痛点** | P4（验证全靠人工） |
| **依赖** | openpyxl |
| **预估开发** | 1 人时 |

#### T-07：docx_structure_extract —— Word 结构提取器

| 项 | 内容 |
|---|------|
| **输入** | `--input <docx路径>` `--output <输出路径>` `--format txt\|json` |
| **输出** | 标题树（层级+标题文本）+ 段落列表 + 表格列表（行列内容） |
| **核心逻辑** | python-docx 读取 → 遍历段落（提取 Heading 样式层级）→ 遍历表格 → 结构化输出 |
| **解决痛点** | P7（Word 评审无前置工具） |
| **依赖** | python-docx |
| **预估开发** | 1.5 人时 |

### 3.2 技能清单（4 个流程级技能）

#### S-01：xlsx-requirement-review —— Excel 需求评审技能

| 项 | 内容 |
|---|------|
| **触发** | 「评审 xlsx 需求文档」「评审测试管理需求」「需求评审」 |
| **封装流程** | ① T-01 导出全表 → ② 按规则配置做三向一致性检查（界面设计 vs 表单 vs 业务规则）→ ③ T-03 生成评审报告 → ④ T-04 同步台账 |
| **规则配置** | 外置 YAML，定义检查规则（示例见 §3.3） |
| **解决痛点** | P2 + P6 |
| **预估开发** | 3 人时（含规则配置框架） |

#### S-02：xlsx-auto-fix —— Excel 自动修复技能

| 项 | 内容 |
|---|------|
| **触发** | 「自动修复」+ 缺陷清单 |
| **封装流程** | ① 读取缺陷清单 → ② 生成修复指令 JSON → ③ T-05 执行修复 → ④ T-06 验证 → ⑤ T-04 更新台账状态 |
| **安全约束** | 修复前自动备份原文件（`原文件名.bak.xlsx`）；第一轮自动修复，第二轮复核后仍存在严重缺陷则停止 |
| **解决痛点** | P3 + P4 |
| **预估开发** | 2 人时 |

#### S-03：docx-requirement-review —— Word 需求评审技能

| 项 | 内容 |
|---|------|
| **触发** | 「评审 docx 需求文档」「评审 SRS」「评审 Word 文档」 |
| **封装流程** | ① T-07 提取结构 → ② 按 IEEE 830/BABOK v3 逐节检查 → ③ T-03 生成评审报告 → ④ T-04 同步台账 |
| **检查维度** | 完整性（IEEE 830 必含章节）/ 一致性（术语统一+前后引用）/ 可测性（验收标准量化）/ 可追溯性（需求编号唯一） |
| **解决痛点** | P7 |
| **预估开发** | 4 人时 |

#### S-04：review-recheck —— 评审复核技能

| 项 | 内容 |
|---|------|
| **触发** | 「复核」「验证修复结果」 |
| **封装流程** | ① 读取台账中「已整改待复核」缺陷 → ② T-06 逐条验证 → ③ 标记闭环/reopen → ④ 若仍有严重缺陷则停止自动修复、人工介入 |
| **解决痛点** | P4（复核自动化） |
| **预估开发** | 1.5 人时 |

### 3.3 规则配置框架（外置 YAML）

```yaml
# review_rules.yaml —— Excel 需求评审规则配置
rules:
  - id: R-001
    name: 字段权限一致性
    severity: 严重
    description: "界面设计展示的字段，表单中字段权限不得为'不显示'"
    check:
      sheet_ui: "测试管理-界面设计"     # 界面设计工作表
      sheet_form: "表单-*"               # 表单工作表（通配）
      match_field: 列名                  # 按列名匹配
      condition: "ui.displayed == true AND form.permission == '不显示'"
    
  - id: R-002
    name: 下钻参数完整性
    severity: 严重
    description: "下钻规则应包含界面设计中所有独立列作为参数"
    check:
      sheet_rule: "业务规则"
      pattern: "下钻.*查询条件"
      required_params: [测试项, 工作包编号, 测试阶段, 测试类型, 测试批次, 测试轮次]
    
  - id: R-003
    name: 排序规则一致性
    severity: 严重
    description: "界面设计标注排序规则时，表单应体现相同排序"
    check:
      sheet_ui: "测试管理-界面设计"
      sheet_form: "表单-*"
      ui_marker: "排序"
      form_marker: "排序"  # 表单中应存在
    
  - id: R-004
    name: 术语统一
    severity: 主要
    description: "同一概念在所有工作表中应使用统一术语"
    check:
      synonyms:
        - [剩余案例数, 遗留案例数]
        - [剩余缺陷数, 遗留缺陷数]
        - [严重界别, 严重级别]
    
  - id: R-005
    name: 计算字段除零处理
    severity: 一般
    description: "所有百分比/比率计算字段应定义分母为0时的处理规则"
    check:
      pattern: "计算公式.*/"
      require_zero_check: true
```

## 六、预期收益

### 6.1 效率收益

| 流程环节 | 当前耗时 | 工具化后耗时 | 节省 |
|---------|:---:|:---:|:---:|
| xlsx 读取与对比 | 15 min | 2 min | 13 min |
| 评审报告生成 | 10 min | 10 s | ~10 min |
| 修复脚本编写 | 20 min | 3 min | 17 min |
| 修复验证 | 10 min | 30 s | ~10 min |
| 台账更新 | 5 min | 5 s | ~5 min |
| **单次评审全流程** | **~60 min** | **~10 min** | **~50 min（83%↓）** |

### 6.2 质量收益

- **一致性检查自动化**：消除人工逐行对比遗漏风险
- **修复指令版本化**：修复过程可审计、可回溯
- **验证结果客观化**：消除人工验证的主观偏差
- **评审标准统一化**：规则配置 YAML 确保不同项目/版本评审标准一致

### 6.3 可复用性

- 工具层（T-01~T-07）为通用脚本，可被任何项目复用
- 技能层（S-01~S-04）封装完整流程，跨项目直接加载
- 规则配置 YAML 可按项目定制检查规则
