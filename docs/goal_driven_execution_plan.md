# 目标驱动自主执行方案

> **OPT-GOAL-001** | 版本 v1.0 | 2026-09-07 | 编排器增强

## 1. 问题定义

当前编排器的铁律 #15（执行合同闸门）要求每个带副作用操作都走「六段合同」（理解→拆解→清单→确认→执行→复验），虽然安全但交互成本高。以 OPT-REVIEW-002 Phase 3 为例：5 个工具 + 1 个技能的交付过程中，用户需说"继续"/"执行" 6~10 次，每次 Tier 2 操作都需输出清单等待确认。

**核心矛盾**：安全铁律 vs 交互效率。

**解决思路**：**目标明确时批量确认，目标模糊时逐步确认**。

**用户洞察**：给 AI 设定完成目标后，AI 可以围绕目标自主推进，不需要每步确认。这符合行业趋势——ReAct + HITL Gate 将人工审批门前置、执行阶段自治；DORA VSM 将等待时间视为隐藏浪费。

## 2. 方案设计

### 2.1 结构化目标定义（SGD）

用户在下达任务时附带完成目标，AI 解析为结构化格式：

```yaml
goal:
  statement: "实现 OPT-REVIEW-002 Phase 3 全部 5 个工具 + 1 个技能"
  acceptance_criteria:
    - id: AC-1
      description: "T-02/T-07/T-10/T-12/T-13 五个工具可运行"
      verify_method: "python -c 'import tools.xxx'"
    - id: AC-2
      description: "S-03 技能文件存在且路由表已更新"
      verify_method: "grep S-03 SKILL.md"
    - id: AC-3
      description: "单元测试全部通过"
      verify_method: "pytest tests/ -k p3 --tb=short"
  constraints:
    - "不修改 Phase 1/2 已有工具"
    - "所有工具支持 PROJECT_ROOT 注入"
  max_iterations: 10
```

SGD 四要素：
1. **statement**：一句话目标（必填）
2. **acceptance_criteria**：可验证的验收标准列表（必填，至少 1 条）
3. **constraints**：操作边界/禁止项（可选）
4. **max_iterations**：最大自主执行轮次（可选，默认 10）

### 2.2 分级交互模型

| 级别 | 操作类型 | 交互方式 | 示例 |
|:---:|---|---|---|
| Tier 1 | 只读（Read/Grep/LS） | 自由执行，不确认 | 读文件、搜索、列目录 |
| Tier 2 | 范围写（目标相关的项目内文件） | **一次性批量确认** | 创建工具文件、写测试、更新路由表 |
| Tier 3 | 高辐射（推送/删除/全局配置/solidify） | 逐项确认（不变） | git push、solidify、修改全局库 |

**关键变化**：Tier 2 操作在目标驱动模式下合并为一次确认——用户在目标确认时一并批准所有 Tier 2 操作范围，AI 自主推进直到目标达成或遇到 Tier 3 操作。

### 2.3 执行流程

```
用户：任务描述 + 完成目标
         |
         v
   [SGD 解析] -- 目标不明确 --> 向用户澄清（仅一次）
         |
         v (目标明确)
   [执行计划] -- 列出步骤 + 操作清单 + 风险分级
         |
         v
   [一次性确认] -- 用户确认目标 + 计划（确认词）
         |
         v
   [自主执行循环] <-----------------------+
         |                                |
         +-- 执行步骤 N（Tier 1/2 自由）   |
         |                                |
         +-- 遇 Tier 3 --> 逐项确认       |
         |                                |
         +-- [完成度自检]                  |
         |      |                         |
         |      +-- 未全达标 --> 继续循环 --+
         |      |
         |      +-- 全部达标 --> 退出循环
         |
         v
   [一次性交付] 报告 + 证据链 + 固化
```

### 2.4 完成度自检机制

每完成一个执行步骤后，AI 对照验收标准逐项检查：

```python
for ac in goal.acceptance_criteria:
    result = run_verify(ac.verify_method)
    ac.status = "PASS" if result.ok else "FAIL"

if all(ac.status == "PASS" for ac in goal.acceptance_criteria):
    exit_loop("目标达成，进入交付")
elif iteration >= goal.max_iterations:
    exit_loop("达到最大轮次，交接当前进展")
```

### 2.5 安全护栏

| 护栏 | 机制 | 说明 |
|---|---|---|
| 最大轮次 | `max_iterations` 默认 10 | 防止无限循环 |
| 范围锁定 | 操作目标必须在 SGD 范围内 | 超出范围的操作暂停等确认 |
| 铁律不降级 | #7/#7a/#7b/#8/#15 仍生效 | Tier 3 操作仍需逐项确认 |
| 错误熔断 | 连续 2 步失败 → 暂停报告 | 不盲目重试 |
| 用户中断 | 随时可输入"停止"中断 | 保留已完成成果 |

## 3. 行业对标

| 来源 | 实践 | 本方案采纳 |
|---|---|---|
| ReAct + HITL Gate（CSDN 2026-07） | 人工审批门前置，执行阶段自治 | 一次性确认目标后自主执行 |
| Plan-and-Execute（LangGraph） | 规划→执行→反思循环 | 执行循环 + 完成度自检 |
| DORA VSM | 减少等待时间/瓶颈 | 批量确认消除逐步等待 |
| AWS AGENTSEC04-BP02 | 三层风险分级 | Tier 1/2/3 分级交互 |
| 铁律 #15 执行合同 | 六段合同 | 保留为 Tier 3 逐项确认，Tier 2 批量化 |

## 4. 与现有机制的关系

- **不替代铁律 #15**：目标驱动模式是 #15 的「效率变体」，Tier 3 仍走完整六段合同
- **不替代决策引擎**：决策引擎处理事件驱动场景（git.commit/schedule.tick），目标驱动处理任务驱动场景
- **兼容 createGoal**：harness 层 createGoal 可作为 SGD 的简化入口
- **兼容闭环执行系统**：编排器 §闭环 的状态机不变，仅「执行中」状态内部增加自主循环
