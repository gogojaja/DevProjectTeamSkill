## 1. 背景与目标

用户提出 7 项自主 Agent 诉求，要求评估"本项目距一个自主 AI Agent 还有多远"并补齐：

| # | 诉求 |
|---|------|
| 1 | AI 收到任务后能分析接受任务的角色 |
| 2 | 可对任务进行拆分，将不同子任务分给不同角色执行 |
| 3 | 有一个角色做任务分析、指派和验收，确保任务闭环 |
| 4 | 收到任务后提前将需确认的问题一次性与用户确认 |
| 5 | 实施过程中尽量减少交互 |
| 6 | 中间必要的多次交互形成经验，以后类似情况可参考 |
| 7 | 执行中发现偏差可随时打断并修正执行方向 |

**评估起点（v21.19.1）**：整体成熟度 **L3.7 / L5**。核心诊断——**能力零件全都有，但没有一个"协调官"把它们串成默认闭环**。

## 2. 成熟度分级框架（L1–L5，可复用）

| 级 | 名称 | 标志 | 本项目对应机制 |
|----|------|------|---------------|
| L1 | 技能库 | 关键词触发加载 | 触发词速查 |
| L2 | 角色自动路由 | 任务语义自动识别角色 | 优先级 0 `infer_from_task_semantics()` |

| L5 | 自主协调官 + 经验自学习 + 可打断修正 | 默认闭环 + 交互沉淀 + 打断重规划 | §2.4.5 + §2.4.6 + P1 绑定表/收割 |

## 3. 三期实施 Journey（L3.7 → L5.0）

### P-001｜§2.4.5 任务协调官默认流程（v21.20.0，提交 `0fc7a5b`）
- **补齐诉求 #3**（单一协调官闭环 2.5→4.0）。
- 编排器收到任务先做**复杂度判定**：单子任务走现有直接路由**完全不变**（保护简单任务路径）；多子任务（≥2 角色 / ≥2 独立子目标）**自动进** Planner→Dispatcher→Executor→Verifier→闭环，**无需 team/ultrawork 关键词**。
- 验收**按引用绑定** role-governance `check_gate`/`config_audit` 做任务级签署，不新建机制。
- 5 文件，+59/-8。

### P1｜角色绑定表 + 交互自动收割（v21.21.0，提交 `5936add`）
- **P1a 补齐诉求 #2**（拆分分派 3.5→4.5）：team-orchestration v1.2.0→v1.3.0，`dependency-graph.md` 新增 §6「抽象角色（planner/architect/executor/test-engineer/verifier/writer）→ 13 角色包绑定表」+ `resolve_role(abstract_role, task_type)`，Dispatcher 指派从人肉变**可查表**，任务类型沿用编排器 §2.4.2 映射表（单一信息源）。
- **P1b 补齐诉求 #6**（交互形成经验 3→4.5）：self-improve v1.1.0→v1.2.0，新增 `domain/interaction-harvest.md`「交互自动收割」——同类任务确认 ≥N 轮（默认 3）→ 抽取「确认清单模板」→ `create_memory` 沉淀 → 下次 Planner 阶段 `search_memory` 提前复用，交互次数随经验递减。
- 9 文件，+168/-15。（提案卡 closed 留痕：提交 `e7d53da`）

### P2｜§2.4.6 打断-修正-重规划-沉淀闭环（v21.22.0，提交 `5b9a76f`）
- **补齐诉求 #7**（打断修正 3.5→4.5），**L5.0 收官**。
- 五步默认闭环（承接 §2.4.5 协调官闭环的"回退/重规划"边）：
  1. **pause** 暂停 Executor 冻结在制品；
  2. **amend** `goal_check.py --amend --amend-reason` 写 `amendment_history` + 更新 `台账/41_活跃目标.json`（铁律 #13 SGD，禁止静默改方向）；
  3. **replan** `dependency-graph` §4 增量重建受影响子图 + §6 绑定表重新指派；
  4. **detect** `deviation-detection` §5.1 `FeedbackIngestion` 解析 Deviation 登记偏差台账；
  5. **harvest** `lesson-harvesting` §2/§4/§5 + `interaction-harvest` + `create_memory` 沉淀反哺。
- 闭环出口：修正生效回 Executor / 目标不可达升级用户 / **偏差未 resolve 不得交付**（衔接 §2.4.5 Verifier 门禁）。
- 5 文件，+63/-9。

## 5. 关键决策与否决方案

**决策：在编排器 §2.4 增量新增小节（§2.4.5/§2.4.6）+ 子技能加法式增强，而非新增第 14 个"协调官角色包"、也非全量重写 team-orchestration。**

| 否决方案 | 否决理由 |
|---------|---------|
| 仅出提案卡不实施 | 触 role-governance 铁律"不得以纯描述型流程发版"，成熟度不动 |
| 全量一次做完 | 改编排器默认主干（全库最高扇出），阈值误判会错路由每个多步任务；违 self-improve §2.3"每次 ≤3 改进点"；难验证难回退 |
| 新增独立协调官角色包 | 撕碎编排器所有权；触发 11 处 ALL_ROLES 硬编码同步与门禁静默漏检风险 |

**全程纪律**：三期均"按引用绑定现有机制、零新建工具/角色/domain"；无新角色→零 ALL_ROLES 硬编码同步成本；每期 A-lite 提案卡先行、可 `git revert` 单提交回退。
