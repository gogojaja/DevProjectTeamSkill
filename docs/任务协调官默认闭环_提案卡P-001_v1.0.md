## 提案 P-001

- **问题**：自主 Agent 成熟度卡在 L3.7。诉求 #3「一个角色做任务分析、指派、验收、确保闭环」成熟度仅 2.5/5——能力零件齐全（编排器路由 + team-orchestration Planner→Verifier + role-governance 验收门禁 + SGD 自检），但**没有串成默认闭环**：team-orchestration 需用户喊 `team/ultrawork` 关键词才启动，抽象角色(Planner/Executor)未绑定 13 个具体角色包，验收落在阶段级门禁而非任务级闭环。
- **根因**（5-Why）：编排器 §2.4 只有"任务级按需加载"（单任务→角色映射），缺"多子任务→自动拆解→分派→任务级验收"的默认骨架；team-orchestration 被设计为**显式触发**的可选并行层，而非复杂任务的默认路径。
- **改进方案**（最小闭环，加法式，不颠覆）：
  1. 编排器 §2.4 新增 **§2.4.5 任务协调官默认流程（复杂度阈值触发）**：单子任务→现有直接路由不变；多子任务（≥2 角色/≥2 独立子目标）→自动进 Planner→Dispatcher→Executor→Verifier→闭环，无需关键词；
  2. 验收**按引用绑定** role-governance 现有 `check_gate`/`config_audit` 做任务级签署，**不新建机制、不改 role-governance**；
  3. 并行细节/冲突仲裁复用 team-orchestration（仅把触发从关键词升级为复杂度自动判定）。
- **预期收益**：诉求 #3 从 2.5→4.0，整体成熟度 L3.7→L4.3；复杂任务默认获得"分析-指派-验收-闭环"，同时简单任务路径零影响。
- **成本**：低（编排器新增 1 小节 + 版本号；无新角色→零 11 处 ALL_ROLES 硬编码同步；无新工具）。
- **风险**：中→低。主风险=复杂度阈值误判导致简单任务被错误拆解。**缓解**：阈值判定保守（仅 ≥2 独立角色/子目标才升级），单子任务默认走原路径；tabletop 双验证（多子任务进闭环 + 单任务回归）。
- **评估方式**：① 版本一致性/闭环/发布门禁全绿；② tabletop dry-run：多子任务样例走协调官闭环、单任务样例确认直接路由不变；③ 四目录部署 grep 核验。
- **回退方案**：删除 §2.4.5 小节 + 版本回退，`git revert` 单提交即回；solidify 快照可恢复。
- **优先级**：P0（高收益低成本，撬动 L4→L5 的关键枢纽）。
- **后续接口**：P1=team-orchestration 抽象角色→13 角色包绑定表；P2=打断-修正-教训沉淀结构化流程（SGD amend + deviation-detection）；P1-#6=交互模式自动收割触发器。
