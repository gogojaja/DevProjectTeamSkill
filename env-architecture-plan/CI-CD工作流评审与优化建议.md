## 2. 需求对齐分析

### 2.1 需求拆解

你描述的工作流可以拆解为 5 个关键环节：

| 环节 | 需求描述 | 现有方案是否覆盖 |
|------|----------|------------------|
| ① 代码提交 | 本机开发 → push 到 GitHub/Gitee | ✅ 已覆盖（Git 协作是基础） |
| ② 自动拉取 | Macmini 检测到新提交，自动拉取最新版本 | ⚠️ 部分覆盖（提到了 Webhook，但无详细设计） |
| ③ 自动测试 | Macmini 自动组织测试（构建 → 部署 → 运行测试） | ⚠️ 部分覆盖（提到了 CI/CD 和测试环境，但流水线不完整） |
| ④ 结果回传 | 测试结果自动提交回 GitHub/Gitee | ❌ 未覆盖（缺少测试结果回传机制） |
| ⑤ 修复决策 | 开发者选择本机修复 或 远端 Macmini 修复 | ❌ 未覆盖（缺少双模式修复工作流设计） |

### 2.2 需求本质

这个需求的本质是建立一条**「提交即验证」**的自动化反馈环：

```
本机提交 → 远端自动构建+测试 → 结果回传到代码平台 → 开发者基于结果决策修复位置
```

这是业界 CI/CD 的核心模式，但针对你的场景（单人开发 + 自托管 + 双端修复）有几个特殊设计点需要关注：

1. **单服务器三环境共享**：CI 运行不能影响生产环境稳定性
2. **双端修复能力**：既可在本机修，也可在远端直接修（SSH + 远程开发）
3. **GitHub/Gitee 双仓库**：需要支持两个代码托管平台的 Webhook 和状态回写

- **Test 环境定位**：承担完整测试验证 ✅

| 缺项 | 影响 | 优先级 |

## 4. 缺口分析

### 4.1 缺口一：CI 运行器部署与资源隔离

**问题**：现有方案只说「CI/CD 部署在 Dev 环境」，但没说清楚 CI Runner 本身怎么部署、和应用服务是什么关系。

**风险**：如果 CI 构建和测试直接跑在 Dev 环境的应用服务上，会造成资源争抢，甚至拖垮 Dev 环境的正常服务。

**优化方向**：独立 CI Runner 容器，通过 Docker-in-Docker (DinD) 或 Socket 挂载方式构建镜像，与各环境的应用服务完全隔离。

### 4.2 缺口二：测试结果回传机制

**问题**：现有方案没有设计测试结果如何回传到 GitHub/Gitee，开发者 push 之后不知道测试过没过。

**风险**：失去自动化价值，退化为「手动去服务器看日志」的原始模式。

**优化方向**：利用 GitHub/Gitee 的 Commit Status / Check Runs API，将测试结果以状态标签的形式回写到对应的 commit 上，开发者在代码提交页面就能看到结果。测试报告作为 artifact 上传或链接到详情页。

### 4.3 缺口三：双模式修复工作流

**问题**：现有方案默认「开发在本机，测试在远端」，但你提到了「在远端 Macmini 进行修复」的选项，这个工作流没有设计。

**风险**：远端修复后代码如何同步、如何避免两端代码分叉、冲突怎么解决，这些都不清楚。

**优化方向**：设计两条修复路径——
- **本机修复（默认）**：pull 测试结果 → 本地修复 → push → 触发新一轮 CI
- **远端修复（快速验证）**：SSH 登录 Macmini → 在 CI workspace 中直接修改 → 验证通过后 → commit push → 本机 pull 同步

### 4.4 缺口四：多项目与多分支策略

**问题**：多个项目并行时，CI 怎么管理？每个分支都跑 CI 吗？PR 才跑？还是只跑 main 分支？

**风险**：不加控制的话，多项目多分支的 CI 会吃光 Macmini 的资源。

**优化方向**：按项目独立 CI 配置文件，分支策略默认「全分支跑轻量 CI（lint + 单元测试），PR/主干跑全量 CI（构建 + 部署 + 集成测试）」。

### 4.5 缺口五：流水线可视化与通知

**问题**：开发者怎么知道 CI 正在运行？失败了怎么知道？

**风险**：信息不透明导致效率损失。

**优化方向**：CI Web 面板查看状态 + 飞书/邮件通知 + Commit Status 直接嵌入 GitHub/Gitee 页面。

## 5. 优化方案：完整 CI/CD 流水线设计

### 5.1 整体架构

```
┌──────────────────────────────────────────────────────────────────┐
│                        本机（开发端）                             │
│                                                                  │
│  ┌──────────┐    push     ┌──────────────────┐                   │
│  │ 本地开发  │────────────▶│  GitHub / Gitee   │                   │
│  │ (feature) │             │  代码仓库         │                   │
│  └──────────┘             └────────┬─────────┘                   │
│         ▲                         │                             │
│         │  pull 修复结果           │ Webhook                      │
│         │                         ▼                             │
│  ┌──────────┐             ┌──────────────────┐                   │
│  │ 查看测试  │◀────────────│  Commit Status    │                   │
│  │ 结果     │             │  （绿勾/红叉）      │                   │
│  └──────────┘             └──────────────────┘                   │
└──────────────────────────────────────────────────────────────────┘
                              │
                              │ Webhook 触发
                              ▼
┌──────────────────────────────────────────────────────────────────┐
│                     Macmini（CI/测试端）                          │
│                                                                  │
│  ┌───────────────────────────────────────────────────────────┐   │
│  │                    CI Runner（独立容器）                   │   │
│  │                                                           │   │
│  │  ① 接收 Webhook → 拉取代码 → 构建镜像                      │   │
│  │  ② 部署到 Dev 环境 → 冒烟测试                              │   │
│  │  ③ 通过 → 部署到 Test 环境 → 全量测试                      │   │
│  │  ④ 收集测试结果 → 回写 Commit Status → 发送通知             │   │
│  └───────────────────────────────────────────────────────────┘   │
│                                                                  │
│  ┌───────────┐   ┌───────────┐   ┌───────────┐                  │
│  │ Dev 环境  │   │ Test 环境 │   │ Prod 环境 │                  │
│  │ (自动部署) │   │ (版本晋升) │   │ (审批发布) │                  │
│  └───────────┘   └───────────┘   └───────────┘                  │
└──────────────────────────────────────────────────────────────────┘
```

### 5.2 流水线分阶段设计

#### 阶段 1：触发与拉取（Trigger & Pull）

- **触发方式**：GitHub/Gitee Webhook（push 事件 / PR 事件）
- **触发条件**：
  - 所有分支 push → 触发轻量 CI（lint + 单元测试）
  - PR 创建/更新 → 触发全量 CI
  - main/master 分支 push → 触发全量 CI + 自动部署到 Dev
- **拉取策略**：
  - 浅克隆（shallow clone）加速拉取
  - 按项目 + commit hash 缓存依赖（node_modules / venv 等）
  - 并发队列控制（同一时间最多跑 N 个 CI job，避免资源耗尽）

#### 阶段 2：构建（Build）

- **构建方式**：Docker 镜像构建（`docker build`）
- **构建缓存**：利用 Docker layer cache，重复构建时复用未变更的层
- **多阶段构建**：编译阶段和运行阶段分离，减小最终镜像体积
- **构建产物**：镜像打 tag（格式：`<项目名>:<分支名>-<commit短hash>`），存本地镜像仓库

#### 阶段 3：部署到 Dev + 冒烟测试（Smoke）

- **部署**：自动更新 Dev 环境的 docker-compose，切换到新镜像
- **冒烟测试内容**：
  - 服务健康检查（接口返回 200）
  - 核心路径快速验证（3-5 个关键接口）
  - 数据库迁移验证（migration 是否正常执行）
- **通过标准**：全部通过 → 进入下一阶段；失败 → 直接回传失败结果，终止流水线

#### 阶段 4：部署到 Test + 全量测试（Full Test）

> **注意**：仅对 PR 和 main 分支执行全量测试，普通 feature 分支只跑到冒烟测试。

- **部署**：将通过冒烟的版本部署到 Test 环境
- **全量测试套件**：
  - **单元测试**：代码级单元测试覆盖率统计
  - **集成测试**：API 级别全量测试
  - **静态扫描**：代码质量（lint）、安全漏洞（dependency scan）
  - **性能基线**：关键接口响应时间对比（可选，非阻断）
- **测试结果收集**：
  - 单元测试：JUnit XML 格式报告
  - 集成测试：测试用例通过/失败统计
  - 覆盖率：覆盖率百分比 + 趋势
  - 日志：构建日志、测试日志全量保存

#### 阶段 5：结果回传（Report Back）

- **Commit Status**：通过 GitHub/Gitee API 在对应 commit 上标注状态
  - `pending` — CI 正在运行
  - `success` — 全部通过
  - `failure` — 有失败
  - `error` — CI 本身出错
- **测试详情**：
  - 生成 HTML 格式的测试报告
  - 通过 Macmini 上的静态文件服务（如 Nginx）提供访问
  - 在 Commit Status 的详情链接中指向报告 URL
- **通知**：
  - 飞书/邮件通知（仅失败时通知，或每日汇总）
  - 通知内容：项目名、分支、commit、失败用例数、报告链接

### 5.3 流水线配置方式

每个项目在仓库根目录放一个 CI 配置文件（类似 `.github/workflows/ci.yml` 的思路）：

```yaml
# .ci/config.yml — 每个项目自带 CI 配置
project: project-alpha

trigger:
  push:
    branches: ["*"]         # 所有分支 push 都触发
    full_test: ["main", "develop"]  # 这些分支跑全量测试
  pr:
    full_test: true          # PR 都跑全量测试

stages:
  - name: build
    script: docker build -t $IMAGE_TAG .

  - name: smoke
    deploy_to: dev
    script: 
      - npm run test:smoke
    allow_failure: false

  - name: full_test
    deploy_to: test
    only_on: [main, develop, pr]
    script:
      - npm run test:unit
      - npm run test:integration
      - npm run lint
      - npm run scan:deps
    artifacts:
      - coverage/
      - test-results/

notifications:
  - type: feishu
    webhook: $FEISHU_WEBHOOK_URL
    on: [failure, error]   # 只有失败才通知
```

## 6. 双模式修复工作流

你提到「由我来决策在本机进行修复或者在远端的 Macmini 进行修复」，以下是两种模式的详细设计：

### 6.1 模式 A：本机修复（默认推荐）

**适用场景**：常规 bug 修复、功能开发、需要调试工具支持的问题

**工作流**：

```
① 收到测试失败通知（飞书/邮件/GitHub 页面）
        │
        ▼
② 本机 pull 最新代码（确保与远端一致）
        │
        ▼
③ 本地定位问题、修复代码
        │
        ▼
④ 本地运行单元测试验证修复
        │
        ▼
⑤ push 提交 → 触发新一轮 CI
        │
        ▼
⑥ 等待 CI 结果 → 全部通过即修复完成
```

**优点**：
- 开发环境熟悉，工具齐全，调试效率高
- 不会干扰 Macmini 上的其他环境和 CI 任务
- 代码天然在本机，不需要额外同步

**缺点**：
- 有些问题只在远端环境复现（环境差异、数据差异），本地不好调试

### 6.2 模式 B：远端修复（环境相关问题专用）

**适用场景**：只在测试环境复现的 bug、需要真实数据排查的问题、环境配置类问题

**工作流**：

```
① 收到测试失败通知 → 判断需要远端调试
        │
        ▼
② SSH 登录 Macmini → 进入对应项目的 CI workspace
   （或 VS Code Remote SSH 直接打开远端目录）
        │
        ▼
③ 在远端直接修改代码 → 手动触发一次 CI 或本地运行测试
   （快速验证修复是否有效）
        │
        ├─ 修复有效 → ④ 在远端 commit + push
        │                    │
        │                    ▼
        │              ⑤ 触发新一轮 CI 验证
        │                    │
        │                    ▼
        │              ⑥ 本机 pull 同步修复代码
        │
        └─ 修复无效 → 返回继续调试（或放弃，回本机修）
```

**关键设计点**：

| 设计点 | 方案 |
|--------|------|
| **远端开发环境** | CI Runner 为每个项目保留一个 workspace 目录，包含最新代码，可直接编辑 |
| **编辑器选择** | VS Code Remote SSH（推荐，体验接近本地） / Vim / Nano |
| **Git 身份** | 远端使用独立的 Git 身份（如 `ci-bot`），commit author 标注清楚是谁在远端修的 |
| **同步机制** | 远端 push 后，本机 pull 即可同步；禁止两端同时修改同一个分支 |
| **冲突避免** | 远端修复建议在独立分支上操作（如 `fix/xxx-remote`），避免直接在 feature 分支上改 |
| **端口/服务占用** | 远端调试时启动的服务用非标准端口（加偏移量），避免和正式环境冲突 |

### 6.3 两种模式的选择建议

| 场景 | 推荐模式 | 理由 |
|------|----------|------|
| 普通功能开发 | 本机修复 | 效率高、工具全 |
| 单元测试失败 | 本机修复 | 本地就能跑单测 |
| 集成测试失败 | 先本机，复现不了再远端 | 大部分集成问题本地也能复现 |
| 只在 Test 环境复现的 bug | 远端修复 | 环境/数据相关，本地不好模拟 |
| 环境配置问题 | 远端修复 | 需要直接操作环境 |
| 性能调优 | 远端修复 | 需要真实环境数据量 |

> **原则：默认本机修复，远端只用来解决「本地复现不了」的问题。** 远端修复后代码仍然要 push 回仓库，通过 CI 验证后才算完成。

## 7. 工具选型细化

现有方案中提到了「Gitea Actions / Drone」作为 CI/CD 选型，这里做进一步细化和对比：

### 7.1 CI 工具对比

| 工具 | 自托管 | 资源占用 | GitHub/Gitee 集成 | 学习曲线 | 推荐度 |
|------|--------|----------|-------------------|----------|--------|
| **Drone** | ✅ | 低（Go 写的，单二进制） | ✅ Gitee/GitHub 都有 OAuth 插件 | 中 | ⭐⭐⭐⭐⭐ |
| **Woodpecker CI** | ✅ | 很低（Drone 社区分叉版） | ✅ Gitea/GitHub/GitLab | 低 | ⭐⭐⭐⭐ |
| **Gitea Actions** | ✅ | 中 | ❌ 只能和 Gitea 集成 | 低 | ⭐⭐⭐ |
| **GitHub Actions runner** | ⚠️ 只跑 runner | 中 | ✅ 仅 GitHub | 低 | ⭐⭐⭐ |
| **Jenkins** | ✅ | 高（Java + 插件生态） | ✅ 有插件 | 高 | ⭐⭐ |
| **GitLab CI** | ✅ | 很高 | ❌ 要部署全套 GitLab | 中 | ⭐ |

### 7.2 推荐选型：Drone CI

**推荐理由**：

1. **轻量**：单二进制 + Docker runner，Macmini 上跑压力小
2. **与 GitHub/Gitee 都能集成**：通过 Webhook + OAuth，双仓库都能用
3. **Pipeline as Code**：`.drone.yml` 放在每个项目仓库里，版本化管理
4. **Docker 原生**：构建和测试都在 Docker 容器中跑，环境干净
5. **Commit Status 回写**：原生支持 GitHub Status API，Gitee 也有对应插件

**部署架构**：

```
Macmini
├── Drone Server（Web UI + 调度器，1 个容器）
├── Drone Runner（执行器，1 个容器，挂载 Docker Socket）
│   └── 动态启动 CI Job 容器（每个 Pipeline 一个）
├── Docker Registry（本地镜像缓存，可选）
└── 各环境服务（Dev/Test/Prod，与 CI 隔离）
```

### 7.3 测试结果回传的具体实现

**GitHub**：
- Drone 原生支持 GitHub Commit Status API
- 每个 pipeline step 的状态自动同步到 GitHub
- 测试报告可以通过 `gh-pages` 或上传到 Release 来展示

**Gitee**：
- Gitee 有「状态检查」API（`POST /repos/{owner}/{repo}/statuses/{sha}`）
- 可以写一个 Drone 插件（或直接用 curl 脚本）调用 Gitee 的 Status API
- 测试报告上传到 Gitee Release 或存放在 Macmini 的静态文件服务上

**统一方式**：不管是 GitHub 还是 Gitee，最终效果都是——在 commit 页面能看到一个绿勾/红叉，点击能跳转到测试报告详情页。

### 7.4 辅助工具

| 工具 | 用途 | 必要性 |
|------|------|--------|
| Docker Registry | 本地镜像缓存，加速构建 | 推荐 |
| Nexus / Verdaccio | 依赖缓存（npm/pip/maven），加速安装 | 可选 |
| SonarQube | 代码质量分析 | 可选（项目多了再加） |
| TestRail / 自研 | 测试用例管理 | 可选（初期用 Markdown 管理就行） |

## 8. 可行性分析

### 8.1 技术可行性

**结论：完全可行。**

理由：
- Docker + Drone 的组合是业界成熟方案，大量中小团队在用
- GitHub 和 Gitee 都有完善的 Webhook 和 Status API
- Macmini 性能足够支撑轻量 CI（M 系列芯片跑构建很快）
- 单开发者场景下，CI 并发量低，不会有性能瓶颈

### 8.2 资源需求估算

假设同时有 3 个项目，每个项目平均每天 5 次 push：

| 资源 | 预估占用 | 说明 |
|------|----------|------|
| CPU | 1-2 核（峰值） | CI 构建时占用，平时几乎为 0 |
| 内存 | 2-4 GB | CI Job 容器 + 构建缓存 |
| 磁盘 | 10-20 GB | 镜像缓存 + 工作区 + 测试报告 |
| 网络 | 低 | 主要是 git pull 和镜像拉取，有缓存后很小 |

对 Macmini 来说完全在可承受范围内，不会影响生产环境（只要做好资源限制）。

### 8.3 实施复杂度

| 阶段 | 工作量 | 难度 |
|------|--------|------|
| 部署 Drone Server + Runner | 半天 | 低 |
| 配置 GitHub/Gitee Webhook | 2 小时 | 低 |
| 为第一个项目写 CI 配置 | 1 天 | 中（要调试构建脚本） |
| 测试结果回传 + 通知 | 半天 | 中 |
| 多项目模板化 | 半天 | 低 |
| 双模式修复工作流验证 | 半天 | 低 |

**总计：约 3-4 个工作日**可跑通第一个项目的完整 CI 流程。

### 8.4 不可行性因素排查

| 潜在障碍 | 影响 | 应对方案 |
|----------|------|----------|
| GitHub 网络不稳定 | CI 触发可能延迟或失败 | Gitee 作为主仓库，GitHub 作为镜像；Webhook 优先走 Gitee |
| Macmini 性能不足 | CI 排队时间长 | 限制并发数（如同时只跑 1 个 CI Job）；错峰运行 |
| 安全顾虑（CI 访问生产数据） | 数据泄露风险 | CI 只访问 Dev/Test 环境，严禁接触生产数据 |
| 维护成本高 | 工具太多管不过来 | 精简工具链，CI 只用 Drone，不用额外堆工具 |

## 9. 新增风险与应对

在现有方案的 8 项风险基础上，补充 CI/CD 自动化引入的新风险：

| 编号 | 风险描述 | 可能性 | 影响 | 等级 | 应对策略 |
|------|----------|--------|------|------|----------|
| R-09 | CI 任务抢占生产环境资源 | 中 | 较大 | 🟡 中 | Docker CPU/内存配额限制；CI 低优先级运行（nice/ionice）；非工作时间跑重任务 |
| R-10 | Webhook 触发失败导致 CI 漏跑 | 低 | 中等 | 🟡 中 | 双 Webhook（GitHub + Gitee）互备；定时轮询兜底（每 5 分钟检查一次新提交） |
| R-11 | 测试结果回传失败，开发者不知道结果 | 低 | 中等 | 🟡 中 | 本地 git pull 时检查 CI 状态；飞书通知兜底 |
| R-12 | 远端修复造成两端代码分叉 | 中 | 中等 | 🟡 中 | 远端修复用独立分支；禁止直接在共享分支上远端修改；push 后提醒本机 pull |
| R-13 | CI 缓存污染导致构建异常 | 低 | 轻微 | 🟢 低 | 定期清理缓存；提供「清理缓存重新构建」按钮 |
| R-14 | CI 配置错误导致误判（测试没跑但显示通过） | 低 | 严重 | 🟡 中 | CI 配置 Code Review；关键步骤必须显式声明成功条件 |

## 10. 落地优先级建议

建议分三期落地，每一期都有独立的价值：

### 第一期：基础 CI（1 周）

**目标**：实现「push → 自动构建 → 冒烟测试 → 结果回写」的最小闭环

- 部署 Drone CI（Server + Runner）
- 配置 GitHub/Gitee Webhook
- 为 1 个核心项目搭建 CI 流水线（构建 + 单元测试 + 冒烟）
- 实现 Commit Status 回传到 GitHub/Gitee
- 飞书通知（失败时）

### 第二期：全量测试 + Test 环境（1 周）

**目标**：完整的 Dev → Test 晋升 + 全量测试

- 流水线扩展到 Test 环境部署
- 接入完整测试套件（集成测试 + 静态扫描 + 覆盖率）
- 测试报告页面（HTML 报告 + 静态文件服务）
- 多项目 CI 模板化
- 性能基线测试（可选）

### 第三期：双模式修复 + 优化（3-5 天）

**目标**：远端修复工作流 + 效率优化

- VS Code Remote SSH 远端开发环境配置
- 远端修复工作流文档化
- 构建缓存优化（依赖缓存 + Docker layer cache）
- CI 资源监控和告警
- 流水线可视化面板优化
