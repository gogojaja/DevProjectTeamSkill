## 1. 方案概述与设计原则

本方案针对多项目并行开发现状，规划一套从本机开发到远端部署的完整环境体系。核心思路是：**本机作为所有项目的并行开发工作站，Macmini 作为远端承载开发、测试、生产三环境的统一服务器**，通过标准化的晋升路径和工具链，确保代码从开发到生产的可追溯、可回滚、可审计。

### 1.1 设计目标

| 指标 | 目标值 |
|------|--------|
| 独立环境层级 | 3 层（开发/测试/生产） |
| 并行开发项目 | 支持 N 个项目并行 |
| 配置环境隔离 | 100% 隔离 |
| 环境恢复目标 | ≤ 30 分钟从零重建 |

### 1.2 核心设计原则

1. **环境一致性**：开发、测试、生产三环境在操作系统、运行时版本、依赖管理上保持高度一致，仅配置参数不同。遵循 12-Factor 的配置与代码分离原则。
2. **隔离性**：各环境之间网络、存储、进程、配置完全隔离。开发环境改动不影响测试，测试环境数据不流入生产。
3. **可重复性**：环境搭建全部脚本化、声明式（Infrastructure as Code），任何环境都可在 30 分钟内从零重建。
4. **可观测性**：每个环境均有日志、指标、告警三位一体的监控体系，环境状态透明可查，故障可定位。
5. **安全分级**：生产环境实施最严格的访问控制与数据保护；开发/测试环境可适当放宽，但敏感数据必须脱敏。
6. **项目并行**：本机和 Macmini 均支持多项目并行，项目间通过命名空间、端口规划、数据分区实现隔离。

> **参考标准**：本方案参考 12-Factor App（配置分离、构建/发布/运行三阶段）、ATAM 架构权衡分析方法、ISO/IEC 25010 质量模型，以及行业通行的 DTAP（Development/Testing/Acceptance/Production）环境演进模式。

## 2. 环境拓扑总览

整体架构由两个物理节点组成：**本机（Windows 工作站）** 承担全部项目的并行开发，**Macmini（远端服务器）** 承载开发联调、测试验证、生产运行三套环境。两者通过局域网 + Git 仓库协同。

```
┌──────────────────────────────────────────────────────────┐
│              本机（Windows 工作站）                      │
│  ┌──────────────────────┐   ┌──────────────────────┐    │
│  │   并行开发环境        │   │   开发工具链          │    │
│  │   （多项目共存）      │   │ Git·Docker·IDE·CLI  │    │
│  └──────────────────────┘   └──────────────────────┘    │
└───────────────────────────┬──────────────────────────────┘
                            │
                  Git push/pull / SSH / 浏览器
                            │
┌───────────────────────────▼──────────────────────────────┐
│                  Macmini（远端服务器）                    │
│                                                           │
│  ┌─────────────────────────────────────────────────────┐ │
│  │  开发联调环境 (Dev)                                  │ │
│  │  应用服务（热部署）· 开发数据库 · 缓存/队列          │ │
│  └─────────────────────────────────────────────────────┘ │
│                            │                              │
│                    晋升 (CI/CD)                          │
│                            ▼                              │
│  ┌─────────────────────────────────────────────────────┐ │
│  │  测试验证环境 (Test)                                 │ │
│  │  应用服务（稳定版）· 测试数据库（脱敏）· 测试工具    │ │
│  └─────────────────────────────────────────────────────┘ │
│                            │                              │
│                     发布审批                              │
│                            ▼                              │
│  ┌─────────────────────────────────────────────────────┐ │
│  │  生产运行环境 (Prod)                                 │ │
│  │  应用服务（发布版）· 生产数据库 · 监控/告警 · 备份   │ │
│  └─────────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────────┘
```

### 2.1 环境职责划分

| 环境 | 部署位置 | 核心用途 | 数据来源 | 访问控制 | 稳定性要求 |
|------|----------|----------|----------|----------|------------|
| **并行开发** | 本机 Windows | 日常编码、本地调试、多项目并行切换 | Mock / 本地样本数据 | 本机用户独占 | 低（可随时重建） |
| **开发联调 (Dev)** | Macmini | 集成联调、功能预演、CI 自动部署 | 开发构造数据 + 部分脱敏 | 开发团队可访问 | 中（允许短时中断） |
| **测试验证 (Test)** | Macmini | 功能测试、性能测试、安全扫描、UAT | 生产脱敏全量数据 | 测试 + 产品可访问 | 高（测试周期内稳定） |
| **生产运行 (Prod)** | Macmini | 正式对外服务、真实数据运行 | 真实业务数据 | 仅运维/授权人员 | 最高（7×24 可用） |

> **关于 Macmini 三环境共机的说明**：单台 Macmini 承载三个环境，需通过容器化（Docker）+ 网络命名空间 + 资源限制（cgroups）实现严格隔离。若后续业务量增长或安全合规要求升级，可平滑迁移至多机或云环境——方案设计时已预留此扩展路径。

## 3. 本机并行开发环境

本机作为**所有项目的并行开发工作站**，核心挑战是多项目之间的资源冲突（端口、依赖版本、数据库实例等）和快速切换效率。方案以容器化为基础，配合项目级隔离策略实现。

### 3.1 隔离策略

- **Docker Compose 项目化**：每个项目自带 `docker-compose.yml`，定义所需的全部服务（应用、数据库、缓存、队列）。启动即全套环境，停止即释放资源。
- **端口规划表**：统一维护端口分配表，每个项目占用一段端口区间（如 8000-8099），避免冲突。本地反向代理（Traefik）可实现域名访问。
- **版本管理器**：Node.js（nvm）、Python（pyenv）、Java（sdkman）等运行时版本按项目自动切换，通过 `.nvmrc` / `.python-version` 等配置文件声明。
- **Git 多仓库管理**：使用 meta 工具或 monorepo 策略管理多项目代码；每个项目独立分支策略，独立提交历史。

### 3.2 开发工具链

| 类别 | 工具选型 | 用途 |
|------|----------|------|
| 代码编辑 | VS Code / JetBrains 系列 | 主力 IDE，按项目保存 workspace 配置 |
| 容器运行 | Docker Desktop (Windows) | 本地服务容器化、环境一致性保证 |
| 版本控制 | Git + GitHub/Gitee | 代码管理与协作 |
| API 调试 | Postman / Bruno | 接口测试与文档 |
| 数据库管理 | DBeaver / TablePlus | 多数据库统一客户端 |
| 终端 | Windows Terminal + PowerShell | 命令行操作，支持多标签分屏 |
| 远程连接 | SSH + VS Code Remote | 访问 Macmini 远端环境 |

### 3.3 目录结构建议

```
D:\workspace\
├── project-alpha/          # 项目 A
│   ├── src/
│   ├── docker-compose.yml
│   ├── .nvmrc
│   └── .env.local
├── project-beta/           # 项目 B
│   ├── src/
│   ├── docker-compose.yml
│   └── .python-version
├── project-gamma/          # 项目 C
│   └── ...
└── _shared/                # 共享资源
    ├── scripts/            # 通用脚本
    └── certs/              # 本地开发证书
```

> **本机开发环境的核心原则**：本机是「**可随时重建的工作区**」而非数据存储地。所有持久化工作（代码、文档、配置）必须提交到 Git；本地数据库和缓存中的数据视为临时，可随时清空重建。这一原则确保开发者的本机环境不会成为单点故障。

## 4. Macmini — 开发联调环境 (Dev)

开发联调环境部署在 Macmini 上，作为**本机开发与正式测试之间的过渡层**。它承接本机提交的代码，提供集成联调和功能预演能力，是 CI/CD 流水线的第一站。

### 4.1 环境定位

1. **代码集成**：接收本机 push 的最新代码，自动构建并部署，验证多模块集成正确性。
2. **联调预演**：前后端联调、第三方服务对接、接口契约验证的统一环境。
3. **冒烟验证**：每次部署后自动运行冒烟测试套件，通过后才允许晋升到测试环境。

### 4.2 技术配置

| 项目 | 配置说明 |
|------|----------|
| 部署方式 | Docker Compose 多项目编排，项目间独立网络 |
| CI/CD | Git Webhook → 自动构建 → 热部署（开发环境允许频繁部署） |
| 数据库 | 每个项目独立数据库实例，共享数据库服务器（资源复用） |
| 数据策略 | 可随时重置为基准数据集（seed data），支持开发构造数据 |
| 日志 | 容器日志集中收集（Loki / ELK 轻量方案） |
| 访问入口 | 统一反向代理（Nginx / Traefik），按项目域名路由 |

> **Dev 环境的价值**：很多团队跳过开发联调环境，直接从本地跳到测试环境，结果是测试环境频繁被未集成验证的代码污染。Dev 环境作为「**第一道质量闸门**」，可以在不影响测试节奏的前提下，让集成问题在更早阶段暴露和修复。

## 5. Macmini — 测试验证环境 (Test)

测试环境是**发布前的最后验证场**，必须最大程度模拟生产环境的配置和数据规模。所有发布候选版本都必须在测试环境通过完整验证后，才能晋升到生产。

### 5.1 测试类型覆盖

- **功能测试**：手工测试 + 自动化回归测试，验证业务功能正确性。
- **性能测试**：接口响应时间、并发吞吐、资源占用，确保满足性能指标。
- **安全扫描**：依赖漏洞扫描、静态代码安全分析、渗透测试（关键项目）。
- **UAT 验收**：产品/业务方在类生产环境中进行用户验收测试。

### 5.2 数据策略

测试环境的数据质量直接决定测试有效性。采用**生产数据脱敏 + 构造数据补充**的混合策略：

- **定期从生产同步**：每周或每个发布周期从生产库全量导出一次
- **自动化脱敏**：使用脱敏工具对姓名、手机号、邮箱、身份证等敏感字段进行不可逆替换
- **保留数据分布**：脱敏过程保留数据的统计分布特征（如用户量、订单量比例），确保性能测试结果有参考价值
- **边界数据补充**：手动构造一些极端场景数据（超大金额、异常状态、并发冲突等），覆盖测试边界

### 5.3 环境稳定性

**vs 开发环境**：开发环境可以一天部署多次，随时打断。测试环境在测试周期内**冻结部署**，仅在版本切换时更新，确保测试结果的可重复性。

**vs 生产环境**：测试环境在软件版本、配置结构上与生产保持一致，但数据量和访问量低于生产。性能测试结果需按比例换算后评估生产表现。

## 6. Macmini — 生产运行环境 (Prod)

生产环境是**正式业务运行的载体**，对稳定性、安全性、数据完整性要求最高。所有变更必须经过审批，所有操作必须留痕审计。

### 6.1 运行保障

- **高可用设计**：应用服务多实例 + 负载均衡；数据库主从复制；关键服务健康检查 + 自动重启。
- **数据备份**：数据库每日全量备份 + 实时 binlog；备份保留 30 天；定期恢复演练验证备份有效性。
- **监控告警**：系统指标（CPU/内存/磁盘）、应用指标（QPS/响应时间/错误率）、业务指标（订单量/用户量）全链路监控。
- **发布管控**：生产发布必须走审批流程；采用蓝绿部署或滚动发布；发布失败自动回滚。

### 6.2 访问控制

| 访问类型 | 控制方式 | 审计 |
|----------|----------|------|
| SSH 登录 | 密钥认证 + IP 白名单 + 跳板机 | 操作日志全记录 |
| 数据库访问 | 独立账号 + 最小权限 + 只读/读写分离 | 查询审计日志 |
| 管理后台 | 双因素认证 (2FA) + 操作审批 | 操作流水记录 |
| API 访问 | Token / 签名认证 + 速率限制 | 访问日志 |

> **生产环境铁律**
> - 禁止在生产环境直接修改代码或配置，所有变更必须通过发布流程
> - 禁止在生产环境进行调试操作，调试一律在测试环境完成
> - 生产数据禁止下载到开发/测试环境（脱敏后才可使用）
> - 生产环境所有操作必须有第二人复核或自动化校验

## 7. 代码晋升与环境流转

代码从本地到生产需经过一条标准化的晋升路径，每个阶段有明确的准入条件和准出条件，确保**只有经过验证的代码才能进入下一个环境**。

```
本机开发 (feature 分支)
       │ push & PR
       ▼
Dev 环境 (CI 自动部署)
       │ 冒烟测试通过 + 代码评审通过
       ▼
Test 环境 (发布候选版本)
       │ 功能/性能/安全/UAT 全部通过
       ▼
Prod 环境 (审批后发布)
```

### 7.1 各阶段门禁条件

| 阶段 | 准入条件 | 准出条件 | 负责人 |
|------|----------|----------|--------|
| **本机 → Dev** | 代码编译通过、单元测试通过 | 冒烟测试通过、代码评审 (Code Review) 通过 | 开发工程师 |
| **Dev → Test** | Dev 环境稳定运行 ≥ 24 小时、无阻断性 Bug | 测试计划评审通过、测试环境部署完成 | 开发负责人 + 测试负责人 |
| **Test → Prod** | 功能测试 100% 通过、性能达标、安全无高危、UAT 通过 | 发布审批通过、回滚方案就绪、运维确认 | 项目经理 + 运维负责人 |

### 7.2 回滚机制

每个环境都支持一键回滚到上一个稳定版本：

- **应用层**：保留最近 N 个版本的镜像 / 构建产物，回滚即切换版本
- **数据库**：迁移脚本必须同时包含 upgrade 和 rollback 两个方向；大版本变更前先备份
- **配置**：配置变更纳入版本控制，回滚即切回上一版配置
- **生产回滚 RTO**：目标 ≤ 5 分钟完成应用层回滚

## 8. 基础设施与工具选型

### 8.1 容器化与编排

Macmini 三环境均以 Docker 为基础运行时，使用 Docker Compose 进行单机编排。选型理由：

- 轻量，适合单服务器多环境场景
- 声明式配置，环境可重复构建
- 生态成熟，几乎所有主流服务都有官方镜像
- 未来扩展到多机集群时，可平滑迁移到 Docker Swarm 或 Kubernetes

### 8.2 工具选型矩阵

| 类别 | 工具 | 选型理由 | 部署环境 |
|------|------|----------|----------|
| 反向代理 | Nginx / Traefik | 统一入口、SSL 终结、按域名路由 | 三环境各一套 |
| CI/CD | Gitea Actions / Drone | 轻量自托管，与 Gitee/GitHub Webhook 集成 | Dev 环境 |
| 日志收集 | Loki + Promtail | 轻量日志方案，资源占用低 | 三环境集中 |
| 指标监控 | Prometheus + Grafana | 行业标准，生态丰富 | 三环境集中 |
| 告警 | Alertmanager + 飞书/邮件 | 灵活的告警路由和分组 | Prod 为主 |
| 数据库 | PostgreSQL / MySQL | 按项目需求选择，容器化部署 | 各环境独立实例 |
| 缓存 | Redis | 高性能 KV 缓存 + 消息队列 | 各环境独立实例 |
| 密钥管理 | 环境变量 + .env 文件 | 初期轻量方案；后续可升级到 Vault | 各环境独立 |

> **选型原则：够用就好，按需升级**。初期阶段以轻量、易维护为优先，不追求一步到位上 Kubernetes 或全套云原生工具。随着项目数量和业务量增长，按实际需要逐步升级——每次升级都有明确的痛点驱动和收益预期，避免过早优化。

## 9. 配置与密钥管理

环境隔离的核心是**配置隔离**。遵循 12-Factor 的「配置与代码严格分离」原则，同一套代码在不同环境中通过注入不同配置来运行。

### 9.1 配置分级

| 级别 | 内容示例 | 存储方式 | 是否入库 |
|------|----------|----------|----------|
| **公开配置** | 服务端口、日志级别、默认超时时间 | 代码中的配置文件（如 `config/default.yaml`） | 是 |
| **环境差异配置** | 数据库地址、缓存地址、外部 API 端点 | 环境变量 + 各环境 `.env` 文件 | 仅示例模板入库 |
| **敏感密钥** | 数据库密码、API Key、Token、私钥 | 独立密钥存储（初期 .env + 文件权限，后期 Vault） | 绝对禁止 |

### 9.2 密钥管理方案

1. **初期方案（当前）**：使用 `.env` 文件 + 严格文件权限（600）+ Git ignore 排除。密钥由运维人员手动部署到各环境。
2. **中期方案**：部署轻量密钥管理服务（如 Infisical 或 Vault），各环境通过服务身份拉取密钥，密钥轮换自动化。
3. **远期方案**：接入硬件安全模块（HSM）或云厂商 KMS，满足更高等级的安全合规要求。

> **密钥安全红线**
> - 密钥和凭据严禁写入 Git 仓库（已通过 pre-commit 钩子检查）
> - 生产环境密钥仅限授权人员知晓，开发人员不应拥有生产密钥
> - 密钥定期轮换（至少每季度一次）
> - 人员离职或权限变更时，立即轮换相关密钥

## 10. 监控与运维

三环境均纳入统一监控体系，但监控粒度和告警级别随环境重要性递增：开发环境仅做基础监控，测试环境增加应用层监控，生产环境实施全链路监控 + 实时告警。

### 10.1 三层监控体系

- **Ⅰ 基础设施层**：CPU / 内存 / 磁盘 / 网络；容器运行状态；磁盘空间预警
- **Ⅱ 应用服务层**：QPS / 响应时间 / 错误率；接口调用拓扑；慢查询 / 异常日志
- **Ⅲ 业务指标层**：核心业务量（订单/用户/营收）；转化漏斗；异常业务模式告警

### 10.2 告警分级

| 级别 | 触发条件 | 通知方式 | 响应时间 |
|------|----------|----------|----------|
| **P0 紧急** | 生产服务不可用、数据异常、安全事件 | 电话 + 短信 + 即时消息 | ≤ 15 分钟 |
| **P1 重要** | 性能下降、部分功能异常、资源接近阈值 | 即时消息 + 邮件 | ≤ 1 小时 |
| **P2 一般** | 非核心指标波动、日志预警、趋势性变化 | 邮件 / 每日汇总 | ≤ 1 工作日 |

### 10.3 运维操作

- **日常巡检**：每日自动生成健康报告，人工确认关键指标
- **备份验证**：每月执行一次恢复演练，验证备份有效性
- **安全补丁**：定期更新系统和应用依赖的安全补丁
- **容量规划**：每季度评估资源使用率，预判扩容需求

## 11. 安全与合规

安全是多环境架构中不可忽视的维度。各环境按重要性实施差异化的安全措施，但**最低安全基线**必须全部达标。

### 11.1 安全基线

| 安全域 | 基线要求 | Dev | Test | Prod |
|--------|----------|-----|------|------|
| 网络隔离 | 环境间网络不可直达 | ✓ | ✓ | ✓ |
| 访问认证 | 禁止弱密码、强制密钥登录 | ✓ | ✓ | ✓ |
| 传输加密 | HTTPS / SSH 加密传输 | △ | ✓ | ✓ |
| 数据脱敏 | 非生产环境不得使用真实敏感数据 | △ | ✓ | — |
| 漏洞扫描 | 定期扫描依赖和镜像漏洞 | △ | ✓ | ✓ |
| 操作审计 | 关键操作全量日志留痕 | — | △ | ✓ |
| 入侵检测 | 异常登录 / 异常操作检测 | — | — | ✓ |
| 容灾备份 | 数据定期备份 + 异地存储 | — | △ | ✓ |

> ✓ = 必须满足　△ = 建议满足　— = 不要求

### 11.2 数据安全

**生产数据**：
- 加密存储（数据库透明加密 / 字段级加密）
- 定期备份 + 异地存储
- 访问最小权限原则
- 操作审计全留痕

**非生产数据**：
- 生产数据导入前必须脱敏
- 脱敏不可逆，且保留数据分布
- 开发环境鼓励使用构造数据 / Mock 数据
- 测试环境可使用脱敏后的生产快照

## 12. ATAM 架构评审

> 基于 SEI ATAM（Architecture Tradeoff Analysis Method）方法，从质量属性维度对方案进行系统评审，识别风险点和权衡决策。

### 12.1 质量属性评估

按 ISO 25010 质量模型对方案在各维度的表现进行评级：

| 质量属性 | 评估说明 | 评级 |
|----------|----------|------|
| **性能效率** | 单机承载三环境存在资源争抢风险；生产环境需设置资源上限和优先级。当前业务量下可满足，但需监控资源使用率。 | ⚠️ 中等 |
| **可靠性** | 单台 Macmini 存在硬件单点故障风险；无异地容灾。生产环境通过多实例 + 备份可部分缓解，但硬件故障仍会导致服务中断。 | ⚠️ 中等 |
| **安全性** | 环境隔离 + 密钥分级 + 数据脱敏 + 访问控制，安全体系完整。但单服务器共享内核和网络栈，隔离强度低于物理隔离。 | ⚠️ 中等 |
| **可维护性** | 容器化 + 声明式配置 + IaC，环境可重复构建；统一监控降低运维复杂度。单服务器运维量可控，维护成本低。 | ✅ 良好 |
| **可扩展性** | Docker Compose 方案可平滑迁移到 Kubernetes；预留了水平扩展路径。初期轻量，后续按需升级。 | ✅ 良好 |
| **可移植性** | 基于 Docker 容器，可在不同硬件和云环境间迁移。架构不绑定特定云厂商或硬件平台。 | ✅ 良好 |

### 12.2 关键权衡分析

| 权衡点 | 选择 | 收益 | 代价 | 缓解措施 |
|--------|------|------|------|----------|
| 单机 vs 多机 | Macmini 单承载三环境 | 成本低、运维简单、资源利用率高 | 硬件单点故障、资源争抢、隔离强度有限 | 资源限制（cgroups）、定期备份、预留扩容路径 |
| 容器化 vs 虚拟机 | Docker 容器化隔离 | 轻量、快速部署、资源效率高 | 隔离强度低于 VM、共享内核 | 网络命名空间、用户 namespace、安全扫描 |
| 自研工具 vs 商业方案 | 开源工具链（Prometheus、Loki、Gitea） | 成本低、可定制、无厂商锁定 | 需要自行维护、学习成本 | 选择成熟度高的工具、文档化运维流程 |
| 环境数量 | Dev + Test + Prod 三环境 | 质量保障充分、职责清晰 | 资源占用多、发布流程较长 | 优化 CI/CD 效率、资源按需启停 |

### 12.3 架构敏感点

以下设计决策对质量属性影响最大，是后续变更时需要重点关注的敏感点：

1. **单机承载三环境** — 影响可靠性、安全性、性能效率。任何硬件升级或迁移都会影响所有环境。
2. **Docker Compose 编排** — 影响可扩展性、可靠性。当业务量增长到单机瓶颈时，需要向 Kubernetes 迁移，这是一个架构级变更。
3. **.env 密钥管理** — 影响安全性。初期方案足够简单，但随项目增多和团队扩大，需尽早规划升级到专业密钥管理系统。
4. **单仓库多项目** — 影响可维护性、可移植性。项目数量增加后，代码组织和依赖管理的复杂度会上升。

## 13. 风险评估与应对

基于 ATAM 评审结果，识别出以下主要风险，并制定相应的应对策略：

| 编号 | 风险描述 | 可能性 | 影响 | 等级 | 应对策略 |
|------|----------|--------|------|------|----------|
| R-01 | Macmini 硬件故障导致全环境中断 | 低 | 严重 | 🔴 高 | 定期备份 + 备用设备预案；关键数据异地备份；制定硬件故障恢复流程 |
| R-02 | 环境间资源争抢（如测试压测影响生产） | 中 | 较大 | 🔴 高 | Docker 资源限制（CPU/内存配额）；压测在闲时执行；监控资源使用率告警 |
| R-03 | 生产数据泄露到非生产环境 | 中 | 严重 | 🔴 高 | 强制脱敏流程 + 审核；开发环境禁止访问生产库；网络 ACL 隔离 |
| R-04 | 密钥泄露（.env 文件管理不当） | 中 | 严重 | 🔴 高 | Git 钩子拦截密钥提交；文件权限 600；定期轮换；中期升级到 Vault |
| R-05 | 配置漂移（各环境配置不一致） | 中 | 中等 | 🟡 中 | 配置模板化 + 版本控制；环境配置审计工具；IaC 声明式部署 |
| R-06 | 多项目端口/命名冲突 | 高 | 轻微 | 🟡 中 | 统一端口规划表；反向代理按域名路由；项目命名规范 |
| R-07 | 备份失效（未定期验证） | 中 | 严重 | 🟡 中 | 每月恢复演练；备份监控告警；多重备份策略 |
| R-08 | 运维知识集中（单点依赖） | 中 | 中等 | 🟡 中 | 运维文档化 + 自动化脚本；至少两人掌握完整运维能力 |

> **高风险项优先处理**：R-01（硬件单点）、R-02（资源争抢）、R-03（数据泄露）、R-04（密钥泄露）为高风险项，建议在环境落地实施阶段优先落实对应的缓解措施。其中 R-02 和 R-03 可通过技术手段直接解决，R-01 和 R-04 需要结合流程和备用方案共同应对。

## 14. 实施路线图

> 本路线图为建议性规划，**暂不落地**，待方案评审通过后再启动实施。

### 第一阶段 · 基础搭建（预计 1-2 周）

Macmini 系统初始化、Docker 环境安装、网络规划、域名配置、安全基线加固（SSH 密钥登录、防火墙、自动更新）。建立端口规划表和项目命名规范。

### 第二阶段 · 开发环境（预计 1 周）

部署 CI/CD 流水线、反向代理、开发数据库和缓存。配置 Git Webhook 自动构建部署。接入第一个项目验证联调流程。

### 第三阶段 · 测试环境（预计 1 周）

部署测试环境全套服务，配置数据脱敏流程，部署测试工具（自动化测试框架、性能测试工具）。建立发布候选版本的晋升流程。

### 第四阶段 · 生产环境（预计 1-2 周）

生产环境高可用部署、监控告警体系、备份策略、安全加固、访问控制。制定发布审批流程和回滚预案。进行首次生产发布演练。

### 第五阶段 · 运维体系（预计 1 周）

统一监控面板、告警分级、日志集中收集、运维文档编写、备份恢复演练、安全扫描纳入流水线。

### 第六阶段 · 持续优化（长期）

根据实际运行情况持续优化：资源调整、工具升级、安全加固、流程改进。定期进行架构评审和风险重评估。

> **总体预估**：完整落地约需 **5-7 周**，可按优先级分阶段交付。第一阶段完成后即可开始使用开发环境，生产环境可在业务需要时再启动建设。

## 15. 评审结论

### 评审结论：方案通过，建议按规划实施

- **架构合理性**：本机并行开发 + Macmini 三环境的分层架构符合行业最佳实践，环境职责清晰，晋升路径明确
- **可扩展性**：基于 Docker 的容器化方案预留了平滑升级路径，可随业务增长逐步演进到集群方案
- **风险可控**：识别出 8 项主要风险，其中 4 项高风险均有明确的缓解措施，整体风险处于可接受范围
- **成本效益**：单服务器承载三环境的方案在初期阶段成本效益最优，避免了过早投入

### 待确认事项

方案落地前，需确认以下事项：

1. Macmini 的硬件配置（CPU/内存/存储）是否满足预期项目数量的资源需求
2. 生产环境是否有明确的 SLA 要求（可用性目标、RTO/RPO 指标）
3. 预计并行的项目数量和技术栈分布
4. 是否有等保、合规等外部安全要求
5. 团队规模和运维人员配置情况

### 后续动作

1. **方案评审**：团队评审本方案，收集反馈并调整
2. **需求确认**：确认上述待确认事项，细化资源需求
3. **详细设计**：输出各环境的详细部署文档和实施计划
4. **分阶段实施**：按路线图分阶段落地，每阶段验收后进入下一阶段
