# 定时任务机制架构策略分析报告

## 1. 业务背景与目标

### 1.1 项目背景

DevProjectTeamSkill 是软件研发全生命周期多角色编排技能库，当前缺乏统一的定时任务机制。周期性任务（如巡检、报告生成、同步、备份等）分散在各角色包中，缺乏统一管理、可观测性和可靠性保障。

### 1.2 设计目标

1. **统一调度入口**：提供标准化的定时任务注册、调度、执行框架
2. **可靠执行**：避免漏跑、重复跑，支持失败重试与死信隔离
3. **可观测性**：任务状态、执行日志、失败告警全链路可见
4. **幂等保障**：任务重复执行不产生重复副作用
5. **可扩展性**：支持任务数量从 10 → 1000+ 平滑扩展
6. **跨平台兼容**：支持 macOS / Linux / Windows 三平台

### 1.3 业务场景分析

| 场景分类 | 典型任务 | 频率 | 重要性 | 幂等要求 |
|---------|---------|------|--------|---------|
| 巡检类 | 版本一致性检查、闭环检查、废弃资产清理检查 | 每日/每周 | 中 | 高 |
| 报告类 | 日报/周报生成、进度汇总、质量报告 | 每日/每周 | 中 | 中 |
| 同步类 | 镜像同步、技能库部署同步 | 每次提交/定时 | 高 | 高 |
| 备份类 | 台账备份、基线快照 | 每日/每周 | 高 | 高 |
| 运维类 | 临时文件清理、工作空间整理 | 每日/每周 | 低 | 中 |
| 审计类 | 安全审计扫描、敏感信息检查 | 每日/每周 | 高 | 高 |

## 3. 约束条件

### 3.1 技术约束

| 约束 | 说明 |
|------|------|
| 编程语言 | 以 Python 为主（与现有工具链一致） |
| 运行环境 | 本地单机运行（非分布式），跨平台 |
| 依赖限制 | 优先使用标准库 + 轻量依赖，避免重型框架 |
| 存储 | 优先使用本地文件（CSV/JSON/SQLite），避免外部数据库依赖 |
| 与 TRAE Schedule 工具的关系 | 作为 TRAE 内置 Schedule 能力的补充和增强 |

### 3.2 业务约束

| 约束 | 说明 |
|------|------|
| 无外部服务依赖 | 不能依赖云服务、消息队列等外部基础设施 |
| 离线可用 | 断网环境下定时任务必须正常运行 |
| 安全合规 | 任务执行不能越权访问项目外资源 |
| 可审计 | 所有任务执行必须留痕可追溯 |

### 3.3 成本约束

| 约束 | 说明 |
|------|------|
| 零基础设施成本 | 不采购外部服务，全部本地实现 |
| 低维护成本 | 架构简单，减少长期维护负担 |
| 低资源消耗 | 后台运行，CPU/内存占用低 |

## 4. 技术选型评估

### 4.1 选型维度与权重

| 维度 | 权重 | 说明 |
|------|------|------|
| 可靠性 | 25% | 任务不丢失、不重复、可恢复 |
| 易用性 | 20% | 接入成本、配置复杂度 |
| 可观测性 | 15% | 监控、日志、告警能力 |
| 跨平台 | 15% | macOS/Linux/Windows 兼容性 |
| 可扩展性 | 10% | 任务规模增长能力 |
| 资源消耗 | 10% | CPU/内存/存储占用 |
| 社区成熟度 | 5% | 生态、文档、长期维护 |

### 4.2 候选方案对比

| 方案 | 可靠性 (25%) | 易用性 (20%) | 可观测性 (15%) | 跨平台 (15%) | 可扩展性 (10%) | 资源消耗 (10%) | 成熟度 (5%) | **加权总分** |
|------|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| **方案A：Python APScheduler + SQLite** | 4.0 | 4.5 | 3.5 | 5.0 | 3.5 | 4.5 | 4.0 | **4.20** |
| **方案B：系统 cron + 任务表 + 幂等脚本** | 3.0 | 4.0 | 2.5 | 3.0（Windows弱） | 2.5 | 5.0 | 5.0 | **3.33** |
| **方案C：Celery + Redis + Beat** | 4.0 | 2.5 | 4.0 | 3.5 | 4.5 | 2.0 | 4.5 | **3.55** |
| **方案D：TRAE Schedule + 任务框架** | 3.5 | 5.0 | 3.0 | 5.0 | 3.0 | 4.5 | 3.5 | **3.95** |
| **方案E：Airflow（轻量部署）** | 4.5 | 1.5 | 5.0 | 3.0 | 5.0 | 1.0 | 5.0 | **3.43** |

### 4.3 详细评估

#### 方案A：Python APScheduler + SQLite

- **概述**：APScheduler 是 Python 生态最成熟的任务调度库，支持多种触发器（cron/interval/date），可持久化到 SQLite
- **优势**：轻量、纯 Python、跨平台好、功能丰富（mis-fire 处理、重试、并发控制）
- **劣势**：单进程调度，无分布式能力（本项目不需要），监控能力需自建
- **适用**：单机跨平台、中轻量任务调度

#### 方案B：系统 cron + 任务表 + 幂等脚本

- **概述**：利用系统 cron 触发，配合任务表记录状态，脚本自身实现幂等
- **优势**：最简单、最可靠、零依赖、资源消耗极低
- **劣势**：Windows 兼容性差（任务计划程序 API 不同），状态管理和监控需完全自建，任务管理分散
- **适用**：极简单任务、Linux-only 环境

#### 方案C：Celery + Redis + Beat

- **概述**：Celery Beat 调度 + Redis Broker + Celery Workers
- **优势**：分布式能力强、任务队列成熟、生态好
- **劣势**：依赖 Redis（增加运维成本），架构较重，Windows 支持不佳，对本项目过重
- **适用**：分布式高并发任务场景

#### 方案D：TRAE Schedule + 任务框架

- **概述**：基于 TRAE 内置的 Schedule 工具（cron 表达式 + Agent 执行），封装统一任务框架
- **优势**：与 TRAE 生态深度集成、配置简单、跨平台好、AI Agent 直接执行
- **劣势**：依赖 TRAE 运行时、调度粒度受限于 Schedule 工具、可靠性依赖 TRAE 进程
- **适用**：TRAE 生态内的 AI Agent 任务

#### 方案E：Airflow 轻量部署

- **概述**：Apache Airflow，业界标准 DAG 调度平台
- **优势**：功能最强大、监控最完善、生态最成熟
- **劣势**：架构最重、资源消耗大、部署复杂、对本项目严重过度设计
- **适用**：大规模数据管道、复杂 DAG 场景

### 4.4 推荐方案

**推荐：方案A（Python APScheduler + SQLite）+ 方案D（TRAE Schedule）混合架构**

**理由**：

1. **APScheduler 作为核心调度引擎**：
   - 纯 Python、跨平台、轻量，与现有工具链一致
   - 功能成熟：cron/interval/date 三种触发器、mis-fire 处理、并发控制
   - SQLite 持久化任务状态，进程重启可恢复
   - 资源消耗低，适合本地单机运行

2. **TRAE Schedule 作为用户交互入口**：
   - 用户通过 TRAE Schedule 工具创建/管理定时任务
   - Schedule 的 cron 触发调用 APScheduler 任务框架执行
   - 利用 TRAE 生态的 AI Agent 能力处理复杂任务

3. **分层设计**：
   - 触发层：TRAE Schedule（用户入口）+ APScheduler（核心调度）
   - 执行层：统一任务执行框架（幂等、重试、状态机、日志）
   - 存储层：SQLite（任务元数据）+ CSV（执行记录，与现有台账一致）
   - 观测层：任务控制台 + 告警通知

## 5. ATAM 权衡分析

### 5.1 关键权衡点

| 权衡点 | 选择 | 理由 | 代价 |
|--------|------|------|------|
| 可靠性 vs 简单性 | 优先可靠性 | 任务漏跑/重复跑的代价远高于架构复杂度 | 增加任务状态管理、幂等校验的复杂度 |
| 功能丰富度 vs 资源消耗 | 控制功能范围 | 本项目任务规模不大，不需要分布式能力 | 不支持分布式水平扩展（当前不需要） |
| 自研 vs 开源 | 优先开源（APScheduler） | 成熟库经过验证，减少自研风险 | 需要学习和适配开源库的 API |
| 统一框架 vs 分散实现 | 统一框架 | 降低维护成本，提升可观测性 | 初期需要投入框架建设成本 |

### 5.2 风险评估

| 风险 | 概率 | 影响 | 风险等级 | 应对措施 |
|------|------|------|---------|---------|
| APScheduler 单进程故障导致全部任务停摆 | 中 | 高 | 高 | 进程守护 + 健康检查 + 失败告警；关键任务双重调度 |
| SQLite 并发写入性能瓶颈 | 低 | 中 | 中 | 任务规模小时无影响； WAL 模式提升并发 |
| 任务幂等性实现不完整导致重复副作用 | 中 | 高 | 高 | 框架层强制幂等键校验；代码评审必须检查幂等性 |
| 跨平台行为不一致 | 中 | 中 | 中 | 三平台统一测试；CI 覆盖 macOS/Linux/Windows |
| 任务堆积导致调度延迟 | 低 | 中 | 低 | 并发数限制 + 超时控制 + 堆积告警 |

## 6. 架构策略总结

### 6.1 核心策略

1. **轻量分布式单机架构**：以 APScheduler 为核心调度引擎，SQLite 持久化状态，单进程高可靠运行
2. **幂等优先设计**：框架层强制幂等校验，业务任务必须实现幂等键
3. **状态机驱动**：所有任务遵循统一状态机（PENDING → RUNNING → SUCCESS/FAILED/DLQ）
4. **分层可观测**：执行记录 → 统计报表 → 告警通知，三层可观测体系
5. **TRAE 生态融合**：上层对接 TRAE Schedule 工具，下层对接技能库任务

### 6.2 技术路线

| 层级 | 技术选型 | 说明 |
|------|---------|------|
| 调度引擎 | APScheduler 3.x | Python 生态最成熟的任务调度库 |
| 状态存储 | SQLite | 轻量、零运维、跨平台 |
| 执行记录 | CSV（UTF-8 BOM） | 与现有台账格式一致 |
| 任务定义 | YAML / Python 函数 | 配置式 + 代码式双模式 |
| 告警通知 | 系统通知 + 日志 | 本地通知 + 结构化日志 |
| 用户入口 | TRAE Schedule 工具 | 与 TRAE 生态集成 |
