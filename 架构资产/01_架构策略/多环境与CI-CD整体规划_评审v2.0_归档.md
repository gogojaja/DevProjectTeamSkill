## 1. 方案总览

### 1.1 核心思路

**本机作为并行开发工作站，Macmini 承载三环境 + CI/CD 自动化，通过 Git 仓库和 Webhook 形成「提交即验证」的自动化反馈环。**

```
本机开发 → push → GitHub/Gitee → Webhook → Macmini CI → 自动测试
    ▲                                                    │
    │                                                    ▼
    └──────── 结果回传（Commit Status + 通知）──────────┘
```

### 1.2 设计目标

| 指标 | 目标值 |
|------|--------|
| 独立环境层级 | 3 层（Dev / Test / Prod） |
| 并行开发项目 | 支持 N 个项目并行 |
| 配置环境隔离 | 100% 隔离 |
| CI 反馈时效 | ≤ 10 分钟（轻量 CI）/ ≤ 30 分钟（全量 CI） |
| 环境恢复目标 | ≤ 30 分钟从零重建 |
| 生产回滚 RTO | ≤ 5 分钟（应用层） |

### 1.3 设计原则

1. **环境一致性**：三环境在操作系统、运行时版本、依赖管理上高度一致，仅配置参数不同。遵循 12-Factor 配置与代码分离原则。
2. **隔离性**：各环境之间网络、存储、进程、配置完全隔离。CI 运行器独立部署，不占用应用服务资源。
3. **可重复性**：环境搭建全部脚本化、声明式（IaC），任何环境可在 30 分钟内从零重建。
4. **提交即验证**：代码 push 后自动触发 CI，测试结果自动回传到代码平台，开发者无需手动查询。
5. **安全分级**：生产环境最严，测试环境居中，开发环境适当放宽。敏感数据必须脱敏后才能进入非生产环境。
6. **双模式修复**：支持本机修复（默认）和远端修复（环境相关问题）两种模式，灵活高效。

## 3. 本机并行开发环境

### 3.1 隔离策略

- **Docker Compose 项目化**：每个项目自带 `docker-compose.yml`，启动即全套环境
- **端口规划表**：每个项目分配一段端口区间，避免冲突；Traefik 反向代理实现域名访问
- **版本管理器**：nvm / pyenv / sdkman，通过 `.nvmrc` / `.python-version` 自动切换
- **Git 多仓库管理**：每个项目独立仓库，独立分支策略

### 3.2 目录结构（示例，非真实环境）

```
D:\workspace\                        # 示例路径（方案演示用）
├── project-alpha/
│   ├── src/
│   ├── docker-compose.yml
│   ├── .drone.yml          # CI 配置
│   ├── .nvmrc
│   └── .env.local
├── project-beta/
│   └── ...
└── _shared/
    ├── scripts/
    └── certs/
```

### 3.3 核心原则

本机是**可随时重建的工作区**。所有持久化工作必须提交到 Git；本地数据库和缓存中的数据视为临时，可随时清空重建。

## 4. Macmini 开发联调环境 (Dev)

### 4.1 定位

CI/CD 流水线的第一站，承接最新代码的自动构建、部署和冒烟测试。

### 4.2 配置

| 项目 | 说明 |
|------|------|
| 部署方式 | Docker Compose 多项目编排，项目间独立网络 |
| 触发方式 | CI 自动部署（每次 push 到 feature 分支都部署） |
| 数据库 | 每项目独立库，共享 DB 服务器 |
| 数据策略 | 基准数据集 + 开发构造数据，可随时重置 |
| 日志 | Loki 集中收集 |
| 访问入口 | Traefik 反向代理，按项目域名路由 |

### 4.3 冒烟测试内容

- 服务健康检查（接口 200）
- 核心路径快速验证（3-5 个关键接口）
- 数据库迁移验证

## 5. Macmini 测试验证环境 (Test)

### 5.1 定位

发布前的最后验证场，最大程度模拟生产配置和数据规模。

### 5.2 测试类型

| 类型 | 工具/方式 | 阻断性 |
|------|-----------|--------|
| 单元测试 | 项目自带测试框架（Jest / pytest 等） | 是 |
| 集成测试 | API 级别全量测试 | 是 |
| 静态代码检查 | ESLint / Pylint / SonarQube（可选） | 是 |
| 依赖漏洞扫描 | npm audit / Trivy | 是（高危阻断） |
| 性能测试 | k6 / JMeter | 否（仅对比基线） |
| UAT 验收 | 手工 + 产品确认 | 是（发布前必须） |

### 5.3 数据策略

- 生产数据脱敏后定期同步（每周 / 每发布周期）
- 脱敏保留数据分布特征
- 补充边界场景构造数据

### 5.4 稳定性要求

测试周期内**冻结部署**，仅在版本更新时切换。测试环境部署的是发布候选版本，不是开发中的最新代码。

## 6. Macmini 生产运行环境 (Prod)

### 6.1 运行保障

- **高可用**：应用多实例 + 负载均衡；DB 主从复制；健康检查 + 自动重启
- **数据备份**：每日全量 + 实时 binlog；保留 30 天；每月恢复演练
- **监控告警**：系统 + 应用 + 业务三层全链路监控
- **发布管控**：审批流程 + 蓝绿/滚动发布 + 失败自动回滚

### 6.2 访问控制

| 类型 | 控制方式 | 审计 |
|------|----------|------|
| SSH | 密钥 + IP 白名单 | 操作全记录 |
| DB | 独立账号 + 最小权限 | 查询审计 |
| 管理后台 | 2FA + 操作审批 | 操作流水 |
| API | Token + 速率限制 | 访问日志 |

### 6.3 生产环境铁律

- 禁止直接修改代码或配置，所有变更必须通过发布流程
- 禁止在生产环境调试
- 生产数据禁止下载到非生产环境（脱敏后才可使用）
- 生产操作必须有第二人复核或自动化校验

## 7. CI/CD 自动化流水线

### 7.1 流水线架构

CI 运行器（Drone）独立部署，与三环境应用服务隔离。流水线按阶段执行，每阶段失败立即终止并回传结果。

```
push / PR
   │
   ▼
┌─────────────┐
│  Stage 1:   │   拉取代码 → 依赖安装 → 构建镜像
│  Build      │
└──────┬──────┘
       │ 通过
       ▼
┌─────────────┐
│  Stage 2:   │   部署到 Dev → 冒烟测试
│  Smoke      │
└──────┬──────┘
       │ 通过
       ▼
┌─────────────┐
│  Stage 3:   │   部署到 Test → 全量测试（单测/集成/扫描/覆盖率）
│  Full Test  │
└──────┬──────┘
       │ 通过
       ▼
┌─────────────┐
│  Report     │   回写 Commit Status → 生成测试报告 → 发送通知
└─────────────┘
```

### 7.2 触发策略

| 事件 | 流水线级别 | 说明 |
|------|-----------|------|
| feature 分支 push | 轻量 CI | 构建 + 单元测试 + 冒烟（不跑 Test 环境全量测试） |
| main/develop push | 全量 CI | 构建 + 冒烟 + 全量测试 + 覆盖率 |
| PR 创建/更新 | 全量 CI | 构建 + 冒烟 + 全量测试，结果回写到 PR 页面 |
| tag 发布 | 发布流水线 | 全量测试 + 生产构建 + 待发布（需人工审批） |

### 7.3 五阶段详解

#### Stage 1 — Build（构建）

- 浅克隆代码（shallow clone）
- 依赖缓存（node_modules / venv，按项目 + lock 文件 hash 缓存）
- Docker 多阶段构建镜像
- 镜像打 tag：`<项目>:<分支>-<commit短hash>`
- 本地镜像仓库缓存

#### Stage 2 — Smoke（冒烟测试）

- 自动部署到 Dev 环境（更新 docker-compose 镜像 tag）
- 等待服务就绪（健康检查通过）
- 运行冒烟测试套件
- 失败则终止流水线，回传失败状态

#### Stage 3 — Full Test（全量测试）

> 仅 main/develop 分支和 PR 执行此阶段

- 部署镜像到 Test 环境
- 运行完整测试套件：
  - 单元测试 + 覆盖率统计
  - 集成测试
  - 静态代码检查（lint）
  - 依赖漏洞扫描
- 收集测试结果（JUnit XML / HTML 报告）

#### Stage 4 — Report（结果回传）

- **Commit Status**：通过 GitHub/Gitee API 在 commit 上标注状态（pending / success / failure / error）
- **测试报告**：生成 HTML 报告，通过静态文件服务访问
- **通知**：飞书/邮件通知（失败时立即通知；成功时可选每日汇总）
- **Artifact 归档**：测试报告、覆盖率报告、构建日志保留 30 天

### 7.4 CI 配置方式（示例，非真实环境）

每个项目仓库根目录的 `.drone.yml`：

```yaml
# .drone.yml（方案演示用示例配置，非真实部署）
kind: pipeline
type: docker
name: project-alpha

trigger:
  branch:
    - "*"

steps:
  - name: build
    image: plugins/docker
    settings:
      repo: local-registry/project-alpha
      tags: ${DRONE_COMMIT_BRANCH}-${DRONE_COMMIT_SHA:0:7}
      registry: registry.local

  - name: deploy-dev
    image: appleboy/drone-ssh
    settings:
      host: macmini.local
      script:
        - cd /opt/dev/project-alpha
        - docker-compose pull && docker-compose up -d
    when:
      status: success

  - name: smoke-test
    image: node:20
    commands:
      - npm run test:smoke
    when:
      status: success

  - name: full-test
    image: node:20
    commands:
      - npm run test:unit
      - npm run test:integration
      - npm run lint
    when:
      branch:
        - main
        - develop
      event:
        - push
        - pull_request
```

### 7.5 资源隔离与限制

- CI Runner 与应用服务**完全独立**，使用独立的 Docker 网络
- 每个 CI Job 设置 CPU/内存上限（如 2 CPU / 2GB 内存）
- 并发 CI Job 数量限制（默认同时最多 2 个）
- CI 任务低优先级运行（nice 值调低），不抢占生产资源

## 8. 代码晋升路径

```
本机开发 (feature 分支)
       │ push
       ▼
Dev 环境 (CI 自动部署 + 冒烟测试)
       │ 冒烟通过 + Code Review 通过
       ▼
Test 环境 (PR 合并 → 全量测试)
       │ 全量测试通过 + UAT 通过
       ▼
Prod 环境 (审批 + 发布)
```

### 8.1 各阶段门禁

| 阶段 | 准入条件 | 准出条件 | 负责人 |
|------|----------|----------|--------|
| 本机 → Dev | 代码编译通过 | 冒烟测试通过 + 单元测试通过 | CI 自动 |
| Dev → Test | Dev 环境验证通过 + PR 创建 | 全量测试通过 + Code Review 通过 | 开发工程师 + CI |
| Test → Prod | 功能测试通过 + 性能达标 + 安全无高危 | 发布审批通过 + 回滚方案就绪 | 项目经理/本人 |

### 8.2 回滚机制

- **应用层**：保留最近 N 个版本镜像，回滚即切换 tag
- **数据库**：迁移脚本同时包含 upgrade + rollback；大版本变更前备份
- **配置**：配置版本化管理，回滚即切回上一版本
- **生产回滚 RTO**：≤ 5 分钟

## 9. 双模式修复工作流

### 9.1 模式 A：本机修复（默认）

**适用场景**：常规 bug 修复、功能开发、单元测试失败

```
① 收到测试失败通知
   ↓
② 本机 pull 最新代码
   ↓
③ 本地定位 + 修复
   ↓
④ 本地单元测试验证
   ↓
⑤ push → 触发新一轮 CI
   ↓
⑥ 等待 CI 结果 → 通过即完成
```

### 9.2 模式 B：远端修复（环境相关问题专用）

**适用场景**：只在 Test 环境复现的 bug、性能调优、环境配置问题

```
① 收到失败通知 → 判断需远端调试
   ↓
② SSH / VS Code Remote 登录 Macmini
   ↓
③ 在 CI workspace 中直接修改
   ↓
④ 手动跑测试快速验证
   ↓
⑤ 验证通过 → commit + push（独立分支）
   ↓
⑥ 触发 CI 验证
   ↓
⑦ 本机 pull 同步修复代码
```

### 9.3 关键规则

| 规则 | 说明 |
|------|------|
| **远端修复用独立分支** | 如 `fix/xxx-remote`，避免直接在 feature 分支上改 |
| **禁止两端同改** | 远端修复期间，本机不要在同一分支上提交 |
| **修复后必须 push** | 远端修改完成后立即 push + 触发 CI 验证 |
| **本机同步** | 远端 push 后，本机 pull 同步最新代码 |
| **服务端口隔离** | 远端手动启动的服务用偏移端口，不与正式环境冲突 |

### 9.4 模式选择指南

| 场景 | 推荐模式 |
|------|----------|
| 功能开发 | 本机修复 |
| 单元测试失败 | 本机修复 |
| 集成测试失败 | 先本机，复现不了再远端 |
| 只在 Test 环境复现 | 远端修复 |
| 环境配置问题 | 远端修复 |
| 性能调优 | 远端修复 |

## 10. 基础设施与工具选型

### 10.1 核心选型（方案建议，本仓库归档时已修正 CI 选型为现有 GitHub Actions）

| 类别 | 工具 | 理由 | 部署位置 |
|------|------|------|----------|
| 容器运行时 | Docker Engine + Compose | 轻量、生态成熟、环境一致 | Macmini |
| CI/CD | **Drone CI** | 自托管轻量、Docker 原生、GitHub/Gitee 双支持 | Macmini（独立容器） |
| 反向代理 | Traefik | 自动服务发现、按域名路由、SSL 自动管理 | Macmini（三环境各一套） |
| 日志 | Loki + Promtail | 轻量日志方案，资源占用低 | Macmini 集中 |
| 指标 | Prometheus + Grafana | 行业标准，生态丰富 | Macmini 集中 |
| 告警 | Alertmanager + 飞书 Webhook | 灵活路由、多渠道通知 | Macmini |
| 数据库 | PostgreSQL / MySQL | 按项目需求选择 | 各环境独立实例 |
| 缓存 | Redis | 高性能缓存 + 消息队列 | 各环境独立实例 |
| 本地镜像库 | Registry（Docker 官方） | 镜像缓存、加速构建 | Macmini |
| 静态文件服务 | Nginx | 测试报告、构建产物访问 | Macmini |

### 10.2 选型原则

**够用就好，按需升级。** 初期以轻量、易维护为优先，不追求一步到位。随着业务增长逐步升级：
- CI/CD：Drone → （量大时）Drone + 多 Runner → （集群化）Argo Workflows
- 编排：Docker Compose → （多机）Docker Swarm → （大规模）Kubernetes
- 密钥：.env 文件 → Infisical → HashiCorp Vault

## 11. 配置与密钥管理

### 11.1 配置分级

| 级别 | 示例 | 存储 | 入库 |
|------|------|------|------|
| 公开配置 | 端口、日志级别、超时 | 代码中配置文件 | 是 |
| 环境差异 | DB 地址、API 端点 | 环境变量 + .env | 仅模板入库 |
| 敏感密钥 | 密码、Token、私钥 | 独立密钥存储 | 绝对禁止 |

### 11.2 密钥管理路线图

1. **初期**：`.env` 文件 + 600 权限 + Git ignore + 手动部署
2. **中期**：Infisical（轻量密钥管理服务）+ 服务身份拉取 + 自动轮换
3. **远期**：Vault / 云厂商 KMS（满足更高合规要求）

### 11.3 密钥安全红线

- 严禁写入 Git 仓库（pre-commit 钩子检查）
- 生产密钥仅限授权人员，开发人员不应拥有
- 每季度轮换一次
- 人员离职/权限变更立即轮换

## 14. ATAM 架构评审结论

### 14.1 质量属性评估

| 质量属性 | 评级 | 说明 |
|----------|------|------|
| 性能效率 | ⚠️ 中等 | 单机承载三环境 + CI，存在资源争抢风险；通过 cgroups 限制和优先级调度可缓解 |
| 可靠性 | ⚠️ 中等 | 硬件单点故障风险；通过多实例 + 备份 + 回滚机制部分缓解 |
| 安全性 | ⚠️ 中等 | 隔离体系完整但为容器级，低于物理隔离；密钥初期方案偏简单 |
| 可维护性 | ✅ 良好 | 容器化 + IaC + 自动化 CI，运维效率高，单服务器管理量可控 |
| 可扩展性 | ✅ 良好 | Docker + Compose 可平滑迁移到 Swarm/K8s；Drone 支持多 Runner 扩展 |
| 可移植性 | ✅ 良好 | 全容器化，可在不同硬件/云平台间迁移，无厂商锁定 |
| 可测试性 | ✅ 良好 | CI/CD 流水线 + 三环境分级测试 + 结果自动回传，测试能力强 |

### 14.2 关键权衡

| 权衡点 | 选择 | 收益 | 代价 | 缓解 |
|--------|------|------|------|------|
| 单机 vs 多机 | 单 Macmini 三环境 + CI | 成本低、运维简 | 硬件单点 + 资源争抢 | 资源限制 + 定期备份 + 扩容路径 |
| 容器化 vs VM | Docker 容器隔离 | 轻量、快速 | 隔离强度较低 | 网络 namespace + 用户隔离 + 安全扫描 |
| CI 工具选型 | Drone CI | 轻量、Docker 原生 | 生态不如 GitHub Actions | 插件 + 脚本补足，自托管可控 |
| 双仓库 vs 单仓库 | GitHub + Gitee 双推 | 地缘风险对冲 | 维护两套 Webhook/Status | 统一 CI 配置，双平台适配 |

### 14.3 架构敏感点

1. **单机承载** — 影响可靠性/安全性/性能，任何硬件变更波及全局
2. **Docker Compose 编排** — 影响可扩展性，到瓶颈时需架构级迁移
3. **Drone CI + 自托管** — 影响可维护性，工具本身的维护成本需纳入考虑
4. **.env 密钥管理** — 影响安全性，随项目增加需尽早升级
5. **双模式修复** — 影响可维护性，需严格遵守流程避免代码分叉

## 16. 架构决策记录 (ADR)

> 注意：以下为方案原文 ADR。本仓库归档实际已登记 **ADR-007**（修正本方案与运行态差异），见 `架构资产/03_架构决策/ADR/ADR-007-*`。

### ADR-001：单机承载三环境 + CI

- **状态**：Accepted
- **决策**：使用单台 Macmini 承载 Dev/Test/Prod 三环境 + CI/CD 运行器
- **理由**：初期项目数量少，资源需求低；单服务器运维成本最低；Docker 容器化可满足隔离需求
- **后果**：存在硬件单点风险；资源需要精细分配和监控
- **缓解**：资源限制 + 定期备份 + 预留扩容路径

### ADR-002：Docker Compose 作为编排工具

- **状态**：Accepted
- **降级触发**：项目数 > 5 或单服务器资源不足
- **决策**：使用 Docker Compose 进行单机多容器编排
- **理由**：轻量、简单、声明式配置；适合单服务器场景；学习成本低
- **替代方案**：Kubernetes（过重）、Docker Swarm（可作为中间过渡）

### ADR-003：Drone CI 作为 CI/CD 工具

- **状态**：Accepted
- **决策**：选用 Drone CI 作为自托管 CI/CD 平台
- **理由**：轻量（单二进制）、Docker 原生、GitHub/Gitee 双支持、Pipeline as Code
- **替代方案**：Jenkins（太重）、GitHub Actions runner（只能 GitHub）、Woodpecker（Drone 分叉，社区版）

### ADR-004：双模式修复工作流

- **状态**：Accepted
- **决策**：支持本机修复和远端修复两种模式，默认本机修复
- **理由**：本机开发效率高、工具全；远端修复解决环境相关问题
- **约束**：远端修复必须用独立分支，修复后立即 push 同步

### ADR-005：GitHub + Gitee 双仓库策略

- **状态**：Accepted
- **决策**：Gitee 为主仓库（稳定），GitHub 为镜像（对冲地缘风险）
- **理由**：GitHub 网络不稳定，Gitee 访问稳定；双仓库互备降低风险
- **实现**：CI 同时配置两套 Webhook，结果同时回写两个平台

### ADR-006：.env 文件作为初期密钥管理方案

- **状态**：Accepted（临时方案）
- **升级触发**：项目数 > 3 或团队人数 > 2 人
- **决策**：初期使用 .env 文件 + 严格权限管理密钥
- **理由**：简单直接，零额外维护成本
- **升级路径**：.env → Infisical → Vault
