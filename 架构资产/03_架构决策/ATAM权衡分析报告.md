# ATAM 权衡分析报告

> 版本：v1.0.0　日期：2026-08-21　方法：ATAM（Architecture Tradeoff Analysis Method）

---

## 1. 概述

本文档使用 SEI 的 ATAM 方法，对定时任务系统的架构设计进行权衡分析，识别关键的质量属性权衡点和风险。

## 2. 质量属性优先级

| 优先级 | 质量属性 | 说明 |
|-------|---------|------|
| P0 | 可靠性 | 任务不丢失、不重复、可恢复 |
| P0 | 幂等性 | 重复执行无副作用 |
| P1 | 可观测性 | 状态可见、可追踪、可告警 |
| P1 | 可维护性 | 任务注册简单、配置清晰 |
| P1 | 安全性 | 访问控制、数据安全、审计 |
| P2 | 可扩展性 | 支持任务数量增长 |
| P2 | 跨平台兼容性 | 三平台一致行为 |
| P3 | 性能 | 调度延迟低 |

## 3. 关键权衡点分析

### 3.1 可靠性 vs 简单性

| 维度 | 说明 |
|------|------|
| **质量属性** | 可靠性（P0） vs 可维护性/简单性（P1） |
| **决策点** | 选择 APScheduler + 幂等 + 重试 + 死信 的完整方案，而非简单 cron 脚本 |
| **倾向** | 优先可靠性 |
| **理由** | 任务漏跑或重复执行的业务代价远高于架构复杂度的增加 |
| **代价** | 架构更复杂，代码量更大，学习成本更高 |
| **缓解** | 良好的文档和封装，降低使用门槛；CLI 工具简化操作 |

### 3.2 性能 vs 一致性

| 维度 | 说明 |
|------|------|
| **质量属性** | 性能（P3） vs 可靠性/幂等性（P0） |
| **决策点** | 每次执行前都要做幂等校验（数据库查询），牺牲一点性能换取可靠性 |
| **倾向** | 优先一致性/可靠性 |
| **理由** | 任务调度对性能要求不高（秒级即可），数据一致性是硬要求 |
| **代价** | 每次执行增加 1-2 次数据库查询，延迟约几毫秒 |
| **缓解** | SQLite 本地查询速度快，性能影响可忽略；索引优化 |

### 3.3 可扩展性 vs 简单性

| 维度 | 说明 |
|------|------|
| **质量属性** | 可扩展性（P2） vs 简单性（P1） |
| **决策点** | 选择单进程架构，而非分布式架构 |
| **倾向** | 优先简单性 |
| **理由** | 当前任务规模下，单进程完全够用，分布式是过度设计；简单架构更可靠、更易维护 |
| **代价** | 任务规模大幅增长时需要重构 |
| **缓解** | 架构设计预留扩展空间，可平滑演进到分布式 |

### 3.4 功能丰富度 vs 资源消耗

| 维度 | 说明 |
|------|------|
| **质量属性** | 功能丰富度 vs 资源消耗 |
| **决策点** | 选择轻量 APScheduler，而非重型 Airflow |
| **倾向** | 控制资源消耗，功能满足需求即可 |
| **理由** | 本项目是本地工具，资源占用应该低；Airflow 功能远超需求，资源消耗大 |
| **代价** | 复杂 DAG、可视化等高级功能不支持 |
| **缓解** | 核心功能都有，高级功能可按需扩展 |

### 3.5 安全性 vs 易用性

| 维度 | 说明 |
|------|------|
| **质量属性** | 安全性（P1） vs 易用性/可维护性（P1） |
| **决策点** | 强制幂等校验、访问边界检查、权限控制 |
| **倾向** | 安全优先，兼顾易用 |
| **理由** | 安全是底线，不能妥协；但可以通过良好的设计降低使用门槛 |
| **代价** | 任务接入需要额外配置（幂等键、权限声明） |
| **缓解** | 提供合理的默认值；提供模板和示例；自动化检查工具 |

### 3.6 数据一致性 vs 写入性能

| 维度 | 说明 |
|------|------|
| **质量属性** | 数据一致性 vs 写入性能 |
| **决策点** | SQLite 事务保证一致性，CSV 异步同步 |
| **倾向** | 热数据强一致，冷数据最终一致 |
| **理由** | 任务状态数据必须强一致（不能丢、不能重复）；执行历史记录允许短暂延迟 |
| **代价** | CSV 同步有延迟（几秒到几分钟） |
| **缓解** | 可配置同步频率；关键任务同步写入 |

## 4. 敏感性分析

### 4.1 敏感点识别

| 敏感点 | 影响的质量属性 | 敏感原因 |
|--------|--------------|---------|
| 任务数量增长 | 性能、可扩展性 | 单进程架构的处理能力有上限 |
| 任务失败率升高 | 可靠性、性能 | 重试增加系统负载，可能引发重试风暴 |
| 任务执行时间变长 | 性能、吞吐量 | 长时间任务占用 Worker，影响其他任务调度 |
| SQLite 并发写入 | 性能、一致性 | 写锁可能导致排队 |

### 4.2 阈值估计

| 指标 | 当前设计上限 | 安全阈值 | 告警阈值 |
|------|------------|---------|---------|
| 任务总数 | ~1000 个 | 500 个 | 300 个 |
| 每日执行次数 | ~10000 次 | 5000 次 | 2000 次 |
| 并发执行任务 | 10 个 | 8 个 | 5 个 |
| 平均任务执行时间 | 300 秒 | 120 秒 | 60 秒 |
| 任务失败率 | 5% | 2% | 1% |

## 5. 风险评估

### 5.1 架构风险

| 风险 | 概率 | 影响 | 风险等级 | 缓解措施 |
|------|------|------|---------|---------|
| 单进程故障导致全部任务停摆 | 中 | 高 | 高 | 进程守护 + 健康检查 + 失败告警 |
| 任务幂等性实现不完整 | 中 | 高 | 高 | 框架层强制校验 + 代码评审检查 |
| 跨平台行为不一致 | 中 | 中 | 中 | 三平台统一测试 + CI 覆盖 |
| SQLite 并发写入瓶颈 | 低 | 中 | 低 | WAL 模式 + 读写分离 |
| TRAE 与 APScheduler 状态不一致 | 中 | 中 | 中 | 定期对账 + APScheduler 为准 |

### 5.2 触发重构的条件

当以下任一条件满足时，需要考虑架构演进：

1. 每日任务执行次数超过 10000 次
2. 同时运行的任务数持续超过 10 个
3. 任务平均执行时间超过 5 分钟
4. 单进程稳定性问题频发
5. 需要分布式多节点部署

## 6. 权衡总结

| 权衡对 | 选择 | 理由 |
|--------|------|------|
| 可靠性 vs 简单性 | 可靠性优先 | 任务正确性是硬要求 |
| 一致性 vs 性能 | 一致性优先 | 幂等和状态一致性不能妥协 |
| 可扩展性 vs 简单性 | 简单性优先 | 当前规模不需要分布式 |
| 功能 vs 资源 | 资源优先 | 轻量工具，够用即可 |
| 安全 vs 易用 | 安全优先，兼顾易用 | 安全是底线，通过设计降低门槛 |

## 7. 结论

本架构设计在可靠性和简单性之间做出了合理的权衡——优先保障任务执行的可靠性和正确性，同时通过良好的封装和设计控制复杂度。架构选择与当前项目的规模和需求高度匹配，同时预留了未来扩展的空间。
