# ADR-002：SQLite + CSV 分层存储策略

## 状态

Accepted（已采纳）

## 上下文

定时任务系统需要存储两类数据：
1. **任务元数据和状态**：任务定义、运行状态、锁信息、幂等键——读写频繁，需要事务支持
2. **执行历史记录**：每次执行的明细数据——追加写入，需要可读、可审计、与现有台账兼容

候选存储方案：
- 方案A：纯 SQLite
- 方案B：纯 CSV
- 方案C：SQLite + CSV 分层存储
- 方案D：JSON 文件
- 方案E：外部数据库（MySQL/PostgreSQL）

## 决策

**采用 SQLite + CSV 分层存储策略。**

- **SQLite**：存储任务元数据、运行状态、幂等键——热数据，读写频繁
- **CSV**：存储执行历史记录——冷数据，追加写入，审计追溯

## 理由

1. **各司其职**：
   - SQLite 适合频繁更新的状态数据，支持事务、索引、查询
   - CSV 适合审计追溯的历史数据，人类可读，与现有台账格式一致

2. **零运维成本**：
   - SQLite 是嵌入式数据库，无需部署和维护数据库服务
   - CSV 是纯文本，版本控制友好

3. **兼容性好**：
   - 与现有 `台账/` 目录的 CSV 格式完全一致（UTF-8 with BOM）
   - 遵循项目"禁止 .xlsx"的规范

4. **性能满足需求**：
   - 任务规模（1000+ 任务/日）下 SQLite 性能绰绰有余
   - CSV 追加写入性能极高

5. **跨平台一致**：
   - SQLite 和 CSV 都是跨平台的，三平台行为一致

## 后果

### 正面
- 存储方案简单，运维成本为零
- 热数据性能好，冷数据可读性强
- 与现有台账格式兼容，便于统一管理
- 备份简单（复制文件即可）

### 负面
- 数据分散在两处，需要同步机制
- CSV 查询能力弱，复杂统计需要额外处理
- SQLite 并发写入能力有限（WAL 模式可缓解）

## 同步策略

1. 执行完成后先写入 SQLite（事务保证）
2. 异步批量同步到 CSV（可配置同步间隔）
3. 每日对账，确保数据一致性
4. 90 天后 SQLite 中的执行记录归档到 CSV 后清理

## 替代方案

| 方案 | 拒绝原因 |
|------|---------|
| 纯 SQLite | 执行记录可读性差，与现有台账格式不兼容 |
| 纯 CSV | 状态数据读写性能差，不支持事务和锁 |
| JSON 文件 | 查询能力弱，不支持事务，文件损坏风险高 |
| 外部数据库 | 需要部署运维，增加复杂度和成本，过度设计 |

## 备注

- SQLite 路径：`.secrets/scheduler.db`
- CSV 路径：`台账/31_定时任务执行记录.csv`
- SQLite 使用 WAL 模式提升并发性能
