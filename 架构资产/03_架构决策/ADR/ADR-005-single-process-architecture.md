# ADR-005：单进程架构而非分布式架构

## 状态

Accepted（已采纳）

## 上下文

定时任务系统的部署架构有两种选择：
- 方案A：单进程架构（调度器 + 执行器在同一进程）
- 方案B：分布式架构（调度器集群 + Worker 集群 + 消息队列）

## 决策

**采用单进程架构。**

调度引擎和执行框架在同一 Python 进程中运行，任务在进程内的线程池中执行。

## 理由

### 1. 需求匹配

当前项目的任务规模和场景：
- 任务数量：几十到几百个任务/天
- 任务类型：巡检、报告、备份、同步、审计——都是中低频任务
- 运行环境：本地单机，不需要多节点部署
- 可靠性要求：高，但可通过进程守护 + 快速恢复满足

单进程架构完全可以满足当前需求。

### 2. 简单性原则

- 单进程架构简单，开发、测试、部署、运维成本都低
- 分布式架构需要处理：Leader Election、分布式锁、消息队列、网络分区、一致性等复杂问题
- 分布式架构的复杂度带来的故障点远多于单进程 + 进程守护

### 3. 资源效率

- 单进程内存占用低（几十 MB 级别）
- 分布式架构需要额外的 Broker（Redis/RabbitMQ）、Worker 进程，资源消耗大
- 对于当前规模，分布式架构是严重的过度设计

### 4. 可靠性可接受

单进程的可靠性问题可以通过以下方式缓解：
- **进程守护**：launchd / systemd / Windows 服务保证进程自动重启
- **状态持久化**：SQLite 持久化任务状态，重启后快速恢复
- **健康检查**：心跳检测，异常时告警
- **快速恢复**：进程启动到恢复调度只需几秒

### 5. 未来可演进

如果未来需要分布式能力，可以平滑演进：
- 先引入消息队列，将执行器分离
- 再引入调度器集群，实现高可用
- 架构设计预留了扩展空间

## 单进程可靠性保障措施

| 措施 | 说明 |
|------|------|
| 进程守护 | macOS: launchd / Linux: systemd / Windows: 服务 |
| 状态持久化 | SQLite 存储任务状态和执行记录 |
| 崩溃恢复 | 启动时检查 stalled job，自动重试或标记失败 |
| 健康检查 | 心跳文件 + 定期健康自检 |
| 告警通知 | 进程异常退出、任务堆积、健康检查失败告警 |
| 超时控制 | 任务超时强制终止，防止单个任务阻塞调度器 |
| 并发限制 | 最大并发任务数限制，防止资源耗尽 |

## 后果

### 正面
- 架构简单，开发维护成本低
- 零外部依赖，部署简单
- 资源消耗低
- 调试方便

### 负面
- 单进程故障影响所有任务（通过进程守护缓解）
- 不支持分布式水平扩展（当前不需要）
- 任务执行在同一进程，故障隔离性较弱（通过超时控制 + 子进程执行缓解）

## 替代方案

| 方案 | 拒绝原因 |
|------|---------|
| 分布式架构 | 过度设计，复杂度高，当前需求不需要 |
| 多进程架构 | 增加复杂度，收益有限（可用线程池替代） |

## 演进路径

如果未来需要扩展，按以下路径逐步演进：

```
单进程 + 线程池
    ↓
单进程 + 子进程执行（更好的隔离）
    ↓
调度器 + Worker 进程（本地多进程）
    ↓
分布式调度 + 分布式 Worker（需要时）
```

## 备注

- 执行器类型：ThreadPoolExecutor（默认）
- 最大线程数：10（可配置）
- 进程守护：推荐使用系统级服务管理
- 监控：通过健康检查接口 + 告警实现
