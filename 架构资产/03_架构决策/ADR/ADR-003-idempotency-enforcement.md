# ADR-003：框架层强制幂等校验

## 状态

Accepted（已采纳）

## 上下文

分布式系统中，at-least-once 是常态——任务可能因为网络重试、进程恢复、手动重跑等原因被重复执行。如果任务不是幂等的，重复执行会产生重复副作用（如重复发送通知、重复写入数据、重复扣款等）。

候选方案：
- 方案A：业务任务自行实现幂等
- 方案B：框架层提供幂等工具，业务任务可选使用
- 方案C：框架层强制幂等校验，业务任务必须提供幂等键

## 决策

**采用方案C：框架层强制幂等校验。**

所有任务必须提供幂等键，框架在执行前自动检查幂等键是否已存在成功记录，存在则跳过执行。

## 理由

1. **可靠性优先**：幂等性是任务系统可靠性的基础保障，不能依赖业务开发人员的自觉性

2. **防止人为疏漏**：如果幂等是可选的，总会有任务因为疏忽而忘记实现幂等，导致线上问题

3. **框架层实现成本低**：统一的幂等校验逻辑在框架层实现一次，所有任务自动受益

4. **符合行业最佳实践**：生产级任务系统都将幂等作为强制要求，而非可选功能

5. **调试友好**：幂等键使得任务执行可追踪、可重放、可去重

## 幂等键设计

### 幂等键生成规则

幂等键 = `{task_name}:{business_key}`

| 键类型 | 表达式 | 适用场景 | 示例 |
|--------|--------|---------|------|
| 按日期 | `{task_name}:{date}` | 每日一次的任务 | `daily_backup:2026-08-21` |
| 按业务键 | `{task_name}:{biz_id}` | 有业务唯一标识 | `sync_mirror:commit-abc123` |
| 按运行ID | `{task_name}:{run_id}` | 每次运行唯一 | `report_gen:uuid-xxx` |
| 自定义 | `{task_name}:{custom}` | 自定义规则 | 任务自行指定 |

### 校验流程

```
任务触发
   ↓
生成幂等键
   ↓
检查幂等键是否存在成功记录？
   ├─ 是 → 跳过执行，返回成功（记录 skipped）
   └─ 否 → 获取幂等锁 → 执行业务逻辑
                       ↓
                    执行成功？
                       ├─ 是 → 记录幂等键 → 返回成功
                       └─ 否 → 不记录幂等键 → 返回失败（可重试）
```

## 后果

### 正面
- 所有任务天然幂等，不会因为重复执行产生副作用
- 业务开发人员无需关心幂等实现细节
- 任务执行可追踪、可重放、可去重
- 提高系统整体可靠性

### 负面
- 任务注册时必须提供幂等键表达式，增加了一点点接入成本
- 对于"天然幂等"的任务（如只读查询），略显冗余
- 幂等键设计不合理可能导致误去重或漏去重

### 缓解措施
- 提供默认幂等键策略（按日期），简单任务直接使用
- 提供幂等键调试工具，帮助验证幂等键正确性
- 幂等键表达式支持灵活配置，适应不同场景

## 替代方案

| 方案 | 拒绝原因 |
|------|---------|
| 业务自行实现幂等 | 不可靠，容易遗漏，重复造轮子 |
| 框架提供工具可选使用 | 无法保证所有任务都实现幂等，存在可靠性风险 |

## 备注

- 幂等键存储在 SQLite 的 `idempotency_keys` 表
- 利用数据库唯一约束防止并发重复执行
- 幂等键保留 90 天，过期自动清理
