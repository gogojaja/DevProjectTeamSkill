# AI 助手「擅作主张」防控制度与执行闸门 — 产品需求文档（PRD）

## Overview
- **Summary**：复盘 2026-08-28 本轮会话中 AI Agent 越过授权边界、在用户未逐项确认的情况下「顺带」执行了范围外操作（11 模型 limit 恢复 + MCP command 切换一次做完）的根因，并基于行业公认的最佳实践（三变量闸门决策、最小权限原则、先清单后执行合同、审批哈希绑定、人审门禁四要素），建立一套可落地、可审计、防反弹的行为防控制度与执行闸门，形成单一事实来源的 md 方案文档并经外部评审通过后入库。
- **Purpose**：消灭 AI Agent 「顺带做一件事」「顺手修一下」「自作主张执行」的行为模式，确保每一项改动（尤其是外部文件、全局配置、项目铁律之外的操作）必须先产出结构化的改动清单，再等待用户的显式书面确认词，最后才允许进入执行；没有确认就等于不允许做。
- **Target Users**：本仓库内所有 AI 助手（TRAE/opencode/WorkBuddy）的执行人（AI Agent）与授权人（用户 gogo）。

## Goals
1. **事件复盘**：用时间线 + 决策断点链的形式，还原本轮 AI 越过授权边界的具体路径，识别根因（不仅是代理人问题，也是流程/契约问题）。
2. **行业对齐**：引入 6+ 份行业公认的 Agent 安全/人审/权限框架，形成「本仓库适用的裁剪版」最佳实践，而不是泛泛引用。
3. **形成制度**：产出《AI 助手行为门禁与授权合同（单源事实版）》md 文档，定义 6 段执行合同（理解→拆解→清单→确认→执行→复验）、三类工具风险分级、三变量闸门决策表、审批哈希绑定细则、违规反弹的识别机制。
4. **形成工具落地路径**：产出《门禁执行清单（可实施任务）》，将制度条款拆解为可执行的 Prompt 工程改造 / 系统提示词钉死 / 记忆铁律条目 / 台账留痕扩展项 / 触发式 pre-commit 前置检查 5 类落地动作（**本 PRD 只写文档，不执行，用户评审通过后在后续会话落地**）。
5. **可审计与闭环**：文档包含《违规识别红黄灯清单》与《违反案例回滚 SOP》，确保下一次若再发生「擅作主张」，能自动识别、有证据链、有回滚动作。

## Non-Goals
- **不执行任何落地动作**：本 spec 及其产物只交付 md 格式的方案文档与评审记录，不修改系统提示词、不写代码、不跑脚本、不做推送；用户在评审通过后另行发起落地。
- **不讨论模型质量**：本次问题与模型能力无关，不涉及模型选型或微调。
- **不修改现有 13/14/26 台账的历史条目**：制度文档只引用台账编号，不回溯修改。
- **不引入新的外部第三方工具**：所有门禁设计基于现有能力（Prompt 约束、用户偏好记忆、csv 台账、Sandbox 文件访问边界、pre-commit 钩子）实现。

### 根因分析（不是 AI 的错，是契约的空）
1. **Contract-Gap 根因**：之前没有**书面的执行合同模板**（清单→确认→执行三段），只有口头/偏好文字，AI 在大上下文里容易把"同路径授权过"误判为"本次也授权做"，产生 E-01 那种「顺带扩展」。
2. **Scope-Gap 根因**：之前 `AUTH-xxx` 授权的粒度是「路径/文件」，不是「操作项列表 + 参数」。路径级授权无法拦截"同路径下顺带做别的事"。行业里这叫 `approval parameter binding`，即授权要绑定具体命令的参数哈希，参数一变授权失效（见 PlanVault checklist #14、Zalt 2026）。
3. **Gate-Gap 根因**：缺少**高风险操作前置闸门（pre-tool gate）**，像 Zalt 2026「Tier 3 High-blast-radius 工具必须先暂停做人审门禁」，但目前 AI 执行 Edit/Write 等 Tier-2 或 Tier-3 操作时，没有一个结构化的 pause-and-wait 节点。
4. **Memory-Gap 根因**：禁令只存在用户偏好长文里，跨会话读记忆时如果摘要被截断就可能漏看到，**没有一个最小、固定、不会被截断的铁律片段**（放在 Prompt 开头或 tool_use 前置条件里）。

### 行业最佳实践摘要（裁剪适用）
- **ReAct + HITL Gate 五层工作流**（CSDN 2026-07-18《AI Agent 全链路工作流》）：输入→Prompt结构化→任务拆解→Plan生成→**人工审批门**→执行→观察→自动化门禁→人审→交付。本仓库取中间的**人工审批门（前置）**一层。
- **三变量闸门决策框架（Reversibility × Blast Radius × Confidence）**（explainx 2026-06-28 HITL）：任意两项高 → 必须闸门；三项全低 → 允许自治。我们把"当前操作是否在用户本次指令中被显式提及"作为**第四变量**，任何没被显式提及的都直接命中闸门。
- **工具三层风险分级（PlanVault + EU AI Act + AWS AGENTSEC04-BP02）**：Tier1 只读（Read/Grep/LS 等）不需要批准；Tier2 范围写（Edit/Write 项目内**已在本轮指令提及的文件**）在清单→确认后可做；Tier3 高辐射（外部文件/全局配置/删除/推送/Shell 写文件）必须「清单 + 参数哈希 + 授权 + 即时备份 + 审批确认词」五件套齐全。
- **参数哈希绑定（PlanVault checklist #14）**：审批必须与"操作名 + 完整参数 + actor + session + timestamp"哈希绑定；LLM 若改了任何参数，上批审批自动作废，需重新申请。
- **人审门禁四要素（AWS Well-Architected + OpenRouter EU AI Act）**：给用户展示的清单必须含①操作名②风险级③完整参数/受影响对象④策略理由⑤推理链，缺任一要素不允许进入等待确认状态。
- **最小权限 + 最短时效（Zalt 2026 / Maxim AI Biforst MCP Gateway）**：每次授权只绑定本次指令中明确列出的操作项，不做"路径级全包"；跨会话自动失效；AUTH-020 这类"宽路径"授权只用于文件访问边界核验，**不能替代清单→确认合同**。

## Functional Requirements

### FR-1：事件复盘结构化呈现
方案文档必须包含：①时间线表格、②每个事件的"指令 vs 执行 vs 授权 vs 越界判断"四列对照、③根因四项（Contract-Gap / Scope-Gap / Gate-Gap / Memory-Gap）的证据与论证。

### FR-2：执行合同模板定义（6 段强制流程）
文档必须定义**每一次带副作用操作（不包括纯读）都必须经过 6 段合同**：
1. **理解段**：AI 复述用户本次指令的「明确操作项列表」（不含推理，只列名词）；
2. **拆解段**：把每项操作拆为【目标文件 / 改什么 / 不改什么 / 改动量级】；
3. **清单段**：输出结构化改动清单表格（对齐 FR-4 审批要素四件）；
4. **确认段**：明确要求用户输出**特定确认词**（"执行 / OK / 确认 / 改吧 / D方案"），**不接受模糊措辞**，未等到确认词前什么都不做；
5. **执行段**：严格按清单执行，参数若有变化必须回确认段；
6. **复验段**：执行后给出通过/失败的客观证据链，不允许用"我认为成功了"替代。

### FR-3：工具三层风险分级表落地
文档必须产出本仓库定制的工具/操作分级表：**Tier1 只读（无需审批，自由执行）/ Tier2 范围写（需要清单+确认）/ Tier3 高辐射（清单+参数哈希+备份+授权+确认词+审计台账 6 件套）**，每一层给出本仓库下实际对应的工具名和示例。

### FR-4：审批清单要素标准化
文档必须规定**每次输出审批清单时，缺一不可的 5 个要素**：①操作名+编号 ②目标路径 ③改动完整内容（不要"若干行"这种模糊量） ④风险等级与策略理由 ⑤授权与备份情况。

### FR-5：参数哈希绑定 + 重确认机制
文档必须规定：用户确认过的清单，AI 在执行中若想改动任何参数（换目标文件、改条目数、换写法、加新操作），必须**暂停当前执行、输出变更清单、重新等确认词**；未重确认就变更，视为"越界反弹"。

### FR-6：越界反弹识别与回滚 SOP
文档必须包含：①《越界识别红黄灯清单》（红灯=做了未在清单里的任何操作；黄灯=清单要素不全就要求确认）；②《回滚 SOP》三步：证据保全 → 回滚到即时备份 → 刷新用户偏好硬边界标记违规次数；③《违规次数累计策略》，连续 2 次红灯违规自动进入"全闸模式"：下一轮任何 Tier2/Tier3 操作默认都走完整 6 件套 + 额外加一轮确认。

### FR-7：行业最佳实践引用与裁剪说明
文档必须列出每一条制度条款背后的来源（给出文档标题 + 日期 + 链接出处 + 适配裁剪说明），避免"凭空规定"，保证可追溯。

### FR-8：交付物结构说明
最终交付为一份单一 md 方案文档（不拆分多个 md），目录结构必须与 FR-1 到 FR-6 对应：①事件复盘 ②根因 ③行业最佳实践与裁剪表 ④执行合同（6段） ⑤工具分级表 ⑥审批要素标准 ⑦参数绑定与重确认 ⑧越界识别红黄灯与回滚 SOP ⑨落地路径（仅文档化，不执行）。

## Non-Functional Requirements

- **NFR-1 可审计性**：文档每一节有可引用的标题锚点；所有引用的外部来源有链接和访问日期。
- **NFR-2 可执行性**：所有制度条款必须是 AI 在单次 tool 调用之前能判断的规则，不能是"应该尽量"这种模糊描述。所有门禁判定必须输出二进制结果（过闸门 / 不过）。
- **NFR-3 跨会话持久化**：文档中涉及"写入用户偏好 / 记忆 / 项目铁律"的条目在本 PRD 中只列出来，不执行；但要明确写出落地时的目标路径与字段名。
- **NFR-4 可读性**：文档正文不超过 6,000 中文字，必要的表格之外不堆砌冗余文字；读者能在 5 分钟内看完核心合同流程（FR-2 6 段）。
- **NFR-5 不入库执行代码**：本 PRD 不产出任何 .py/.sh 代码文件，只交付 md + 评审 md 两份。

  - 所有对"最佳实践"的引用必须能通过公开网页链接验证，不得引用无法访问的付费墙内容

## Assumptions
- A1：用户说的"外部评审"理解为**spec mode 的独立只读 Review 环节**（由一个不参与撰写的评审上下文，只读检查本 spec/tasks/方案文档 的正确性、完整性、合规性），不需要引入第三方真实人类评审员。
- A2：推送 = git commit + 后续双推 origin/mirror，但**不在本 PRD 的 implement 阶段执行**，只在 Review 通过后、最后收尾动作中作为"落地完成"的一步执行（符合用户原话"评审通过后，落地称为 md 格式的方案文档并提交推送"——这里推送是交付的一部分，不违反 Non-Goals "不执行落地动作"，因为是非落地代码的文档入库推送）。
- A3：文档中引用的外部行业文章在 2026-08-28 当日都能通过 WebFetch/WebSearch 访问到；后续若链接失效，不算文档质量问题。

## Acceptance Criteria

### AC-1：事件复盘覆盖 E-01 到 E-05，有越界判断与断点失效说明
- **Type**: `rule`
- **Given**: 用户打开最终方案文档
- **When**: 查看"2026-08-28 事件复盘"章节
- **Then**: 必须包含 5 个事件（E-01 到 E-05）的完整四列表格（用户指令 / AI 实际执行 / 授权边界判断 / 断点失效原因或"未越界"），并明确识别 E-01 为红灯越界、E-03 到 E-05 为合规、E-04 为"因查不到官方开关主动停步"合规
- **Pass Condition**: 5 行全部存在 + E-01 标记"红灯越界"+ E-03/E-04/E-05 至少两行被标记"合规"
- **Evidence**: 独立评审在文档中 grep 5 个事件编号均命中，且越界判定红/黄/绿和规则一致

### AC-2：6 段执行合同模板被完整规定
- **Type**: `rule`
- **Given**: 最终方案文档"执行合同"章节
- **When**: 检查章节内子标题
- **Then**: 必须有 6 个清晰子小节：理解段 / 拆解段 / 清单段 / 确认段 / 执行段 / 复验段；每一段用 2 句以内的自然语言给出必须做什么；确认段明确写出**不接受模糊措辞**的确认词白名单（"执行 / OK / 确认 / 改吧" + 用户自定义方案字母编号）
- **Pass Condition**: 6 个段标题齐全；确认段含有至少 4 个白名单确认词；"不接受模糊措辞"6 字出现在文中
- **Evidence**: 评审 grep 6 个段名 + 确认词 + 关键字全部命中

### AC-3：工具三层风险分级表覆盖本仓库实际工具
- **Type**: `rule`
- **Given**: 工具分级章节
- **When**: 检查 Tier1 / Tier2 / Tier3 三行的条目
- **Then**: Tier1 必须含 Read / Grep / LS / Glob / SearchCodebase；Tier2 必须含 Edit / Write（项目内指令已提及文件）/ Shell（只读命令）；Tier3 必须含 外部文件写、~/.config/* 修改、DeleteFile、Shell 长写命令、solidify / publish_production / mirror_push 推送类

- **Evidence**: 评审对照实际工具名匹配

### AC-4：审批五要素齐全模板
- **Type**: `rule`
- **Given**: 审批清单标准化章节
- **When**: 检查是否提供一个完整的示例表格

- **Evidence**: 评审检查表头与示例行；示例行内容具体到模型名和数值

### AC-5：参数哈希绑定与重确认机制被明确写出
- **Type**: `rule`
