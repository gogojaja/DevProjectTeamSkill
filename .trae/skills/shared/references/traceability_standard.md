# 需求-架构-代码 三方一致性标准（Traceability & Conformance）

> 版权声明：`../COPYRIGHT.md`
> 适用：所有启用本技能库的软件项目（对齐 NASA SWE-059 / ISO/IEC/IEEE 24765 / EN 62304 / ASPICE / ArchUnit 思路）
> 调用：阶段流转门禁 `stage_review` / `check_gate` 调用 `tools/check_traceability.py` 自动校验

---

## 1. 问题定义

技能使用过程中反复出现两类漂移（drift）：

- **需求-架构漂移**：架构设计未覆盖需求，或架构引入了需求未要求的能力（gold-plating / 孤儿架构）。
- **架构-代码漂移**：代码模块无对应架构元素（孤儿代码），或架构元素无代码落地（悬空架构）。

根因：**缺乏单一事实来源的双向追溯（bidirectional traceability）**，且追溯未随变更持续维护（只在审计前突击补矩阵）。

---

## 2. 行业最佳实践（依据）

| 来源 | 核心主张 |
|------|----------|
| NASA SWE-059 / ISO 24765 | 需求↔架构↔设计↔代码↔测试 **双向可追溯**，唯一标识，禁止「孤儿」（无父链接的元素） |
| EN 62304（医疗器械） | **4-way traceability**：需求↔设计、需求↔测试、风险↔设计、风险↔测试；孤儿即审计发现项 |
| ASPICE | 架构须证明**每个需求分配到具体组件/接口**；定期「追溯健康自检」发现未覆盖/断链 |
| ArchUnit / 架构一致性 | **架构-实现一致性以自动化检查强制执行**（架构即测试，CI 门禁），杜绝代码漂移 |

结论：**追溯必须连续维护 + 自动化门禁强制**，而非人工临时补表。

---

## 3. 标识符规范（ID Scheme）

所有生命周期产物使用**唯一、稳定、不复用**的前缀标识：

| 产物 | 前缀 | 示例 | 生成阶段 |
|------|------|------|----------|
| 需求 | `REQ-<nnn>` | REQ-001 | 需求分析 |
| 架构决策 | `ADR-<nnn>` | ADR-001 | 架构设计 |
| 架构元素/组件 | `AE-<nnn>` | AE-001 | 架构设计 |
| 代码模块 | `MOD-<nnn>` | MOD-001 | 开发 |
| 测试用例 | `TC-<nnn>` | TC-001 | 测试 |

- 每个需求至少映射 1 个 AE；每个 AE 至少回溯 1 个 REQ（双向）。
- 每个代码模块声明所属 AE；每个 AE 至少 1 个 MOD 实现。
- 每个需求至少 1 个 TC 验证；每个 TC 回溯到至少 1 个 REQ。

---

## 4. 单一事实来源：追溯矩阵

文件：`台账/需求-架构-代码追溯矩阵.csv`（UTF-8 with BOM，CSV 首行表头）

| 列 | 含义 | 多值分隔 |
|----|------|----------|
| `REQ_ID` | 需求标识 | `,` 或 `;` |
| `REQ_TITLE` | 需求标题（人类可读） | — |
| `AE_ID` | 映射的架构元素 | `,` 或 `;` |
| `MOD_ID` | 实现的代码模块 | `,` 或 `;` |
| `TC_ID` | 验证的测试用例 | `,` 或 `;` |

**初始化**：`python3 tools/check_traceability.py --init` 生成空模板。

**示例行**：

```
REQ_ID,REQ_TITLE,AE_ID,MOD_ID,TC_ID
REQ-001,用户可登录,AE-001,MOD-001,TC-001
REQ-002,用户可登出,AE-002,MOD-002,TC-002
```

孤儿登记（无父链接的元素，须立即清理或补链接）：

```
,,AE-003,,            ← 孤儿架构：无回溯需求
,,,MOD-004,           ← 孤儿代码：无归属架构
,,,,TC-005            ← 孤儿测试：无回溯需求
```

## 5. 一致性门禁（自动校验）

`tools/check_traceability.py` 在 `stage_review` / `check_gate` 阶段自动运行，校验六类关系（见 §3）：

1. 需求→架构覆盖（每个 REQ 至少 1 个 AE）
2. 需求→测试覆盖（每个 REQ 至少 1 个 TC）
3. 架构无孤儿（每个 AE 至少回溯 1 个 REQ）
4. 架构已落地（每个 AE 至少 1 个 MOD）
5. 代码无孤儿（每个 MOD 至少归属 1 个 AE）
6. 测试回溯需求（每个 TC 至少回溯 1 个 REQ）

**门禁结论**：违规数 > `--max-violations`（默认 0）则 **exit 1（驳回流转）**；矩阵缺失则提示先建立。
断链率（孤儿数 / 总数）应 **= 0%**；既有项目可设容忍度渐进收敛（参照 ArchUnit `FreezingArchRule` 冻结已知违规、仅报新增）。

## 6. 流程嵌入（何时做）

- **需求分析阶段**：建立 `REQ-<nnn>`，初始化追溯矩阵（仅 REQ 列）。
- **架构设计阶段**：补充 `AE-<nnn>` / `ADR-<nnn>`，完成 需求↔架构 双向映射（`check_gate` 校验无孤儿架构/悬空需求）。
- **开发阶段**：每个 `MOD-<nnn>` 声明所属 AE，补全 架构↔代码 映射（代码评审含「孤儿代码」检查）。
- **测试阶段**：每个 `TC-<nnn>` 回溯 REQ，补全 需求↔测试 映射。
- **每阶段 `stage_review`**：自动跑 `check_traceability.py`，**未通过不得流转**。
- **变更时**：需求/架构/代码任一变更，同步更新矩阵（保持连续追溯，禁止事后突击补表）。

---

## 7. 健康自检清单（借鉴 ASPICE「追溯健康自检」）

每次阶段评审自问，任一「是」即待办：

- [ ] 是否存在无架构映射的需求？（需求-架构断链）
- [ ] 是否存在无代码落地的架构元素？（悬空架构）
- [ ] 是否存在无父架构的代码模块？（孤儿代码）
- [ ] 是否存在无测试验证的需求？（需求-测试断链）
- [ ] 是否存在无回溯需求的测试？（孤儿测试）
- [ ] 最近一次变更是否已同步更新追溯矩阵？
