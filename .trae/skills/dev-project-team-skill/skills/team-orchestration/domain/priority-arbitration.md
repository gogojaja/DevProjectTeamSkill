# 多角色并行优先级仲裁（Priority Arbitration）

> 定位：team-orchestration 编排层的跨角色冲突裁决规则。当多个角色并行产出方案且互相冲突时，按本规则优先级排序裁定，避免各角色各执一词、无限协商。

## 1. 仲裁前提：冲突定义

仅当满足以下条件才进入仲裁：
1. 同一任务/同一交付物，两个及以上角色给出**互斥或不可兼容**的方案（如端口占用、接口契约不一致、架构选型分歧、缺陷严重性分级冲突）；
2. 已尝试自动协商（证据交换 ≤2 轮，见 multi-perspective-validation `aggregation-decision.md` §3.2）仍无共识；
3. 冲突未决将阻塞门禁/基线/交付流转。

不构成冲突：角色职责域内独立结论（各写各的产出物）、顺序依赖的任务（前一角色完成后下一角色接力）。

## 2. 优先级总排序（行业最佳实践）

依据「不可逆性 → 风险安全 → 范围合规 → 质量 → 成本进度」的裁决权重，角色方案优先级从高到低：

| 级别 | 角色（方案来源） | 裁决权重依据（行业实践） |
|------|------------------|--------------------------|
| **P0** | **需求分析师 / 干系人诉求** | IEEE 830 / BABOK：需求基线是唯一权威，实现与需求冲突时以需求为准（需求基线权威铁律） |
| **P0** | **总控保障（role-governance）** | PMBOK：范围/进度/成本/风险/安全五维治理为项目级裁决者；门禁与基线不可绕过 |
| **P1** | **安全评审（SecurityReviewer）** | OWASP ASVS / 合规：高危漏洞、数据泄露、合规违规**一票否决**，优先级高于功能与性能 |
| **P2** | **架构师（Architect）** | ISO/IEC/IEEE 42010：接口契约、技术栈、数据架构为全局决策，变更成本高、不可逆性强 |
| **P3** | **测试工程师（Test）** | ISTQB：缺陷严重性/优先级判定、验收门禁，以需求基线与 RTM 为准 |
| **P4** | **开发工程师（Dev）** | 实现层方案：编码细节、性能优化、实现取舍，服从架构与需求约束 |
| **P5** | **部署/运维（Deployment）** | ITIL v4：发布策略、回滚方案，服务连续性保障 |
| **P6** | **文档/复盘（Doc/其他辅助）** | 交付物记录与归档，不参与方案裁决 |

## 3. 裁决规则（冲突判定）

### 3.1 基本规则
1. **高优先级角色方案优先**：冲突时以级别高者为准；同级别冲突 → 自动协商 → 总控仲裁。
2. **一票否决（P0/P1）**：需求基线合规性、安全高危（严重漏洞/数据泄露/合规违规）、范围蔓延超门禁——任一 P0/P1 判定冲突，立即裁决，禁止协商绕过。
3. **反向否决例外**：任何角色不得以「已实现」为由反向修改 P0（需求基线）；需求基线调整必须走合法需求变更流程。
4. **不同领域冲突按领域权重**：安全 vs 性能 → 安全优先（P1>P4）；架构 vs 开发细节 → 架构优先（P2>P4）；测试判定 vs 开发辩解 → 测试判定优先（P3>P4），除非测试判定违反需求基线。

### 3.2 领域冲突速查表

| 冲突对 | 裁决 | 依据 |
|--------|------|------|
| 安全高危 vs 功能上线 | 安全优先，阻断发布 | 一票否决 |
| 架构接口 vs 开发便利 | 架构优先，开发适配 | 不可逆性 |
| 测试缺陷 vs 开发辩称"已实现" | 测试判定优先，返工 | 需求基线权威 |
| 性能优化 vs 架构约束 | 架构约束优先 | 全局决策 |
| 部署窗口 vs 测试未完成 | 测试完成优先 | 质量门禁 |
| 需求新诉求 vs 既有实现 | 需求优先，走变更流程 | 需求基线权威 |

### 3.3 一致性约束
- 任一角色的方案不得违反 P0 级（需求基线/治理门禁）与 P1 级（安全合规）约束，此为**硬约束**；
- P2~P4 为**软约束**，冲突时按优先级递减，但不得突破硬约束。

## 4. 仲裁流程

```
冲突发生
  → 1. 识别冲突类型与涉事角色（按 §1）
  → 2. 自动协商：证据交换 ≤2 轮（多视角验证 §3.2）
  → 3. 仍未解决 → 按 §2 优先级总排序裁定
  → 4. 涉及 P0/P1 → 总控 change_audit 留痕 + 用户确认
  → 5. 出具《冲突仲裁记录_<对象>.csv》写入范围变更台账
  → 6. 裁决结果同步各角色方案，进入门禁
```

**仲裁记录字段**：`冲突编号 | 涉事角色 | 冲突对象 | 各方方案摘要 | 优先级裁决 | 依据 | 裁决人 | 时间 | 是否升级用户`

## 5. 门禁与刹车

- 仲裁未决 → 相关门禁/基线/流转一律暂停；
- 同一对象 2 次仲裁仍反复 → 升级用户决策（总控 change_audit 留痕），禁止自动无限循环；
- 仲裁结果违反 P0 需求基线或 P1 安全 → 仲裁无效，重新裁决（P0/P1 不可被仲裁推翻）；
- 所有仲裁结果必须留痕，禁止无记录的口头裁决。
