# 方案评审标准与评分规则

> 对齐行业五维评审法，适配 DevProjectTeamSkill 多角色编排体系。

## 五维评审标准

### 1. 完整性 (Completeness) — 权重 25%

| 得分 | 标准 |
|------|------|
| 5 | 所有需求全覆盖，场景无遗漏，边界条件已考虑 |
| 4 | 主要需求全覆盖，少量边界条件缺失 |
| 3 | 核心需求覆盖，部分次要需求遗漏 |
| 2 | 重要需求有遗漏，需补充 |
| 1 | 大量需求未覆盖 |

**检查项**:
- 每个需求都有对应方案段落
- 异常场景/边界条件已考虑
- 变更清单完整列出所有文件

### 2. 可行性 (Feasibility) — 权重 25%

| 得分 | 标准 |
|------|------|
| 5 | 技术成熟、资源充足、无外部依赖风险 |
| 4 | 技术可行，少量资源需协调 |
| 3 | 技术基本可行，存在一定不确定性 |
| 2 | 技术路线有风险，需额外验证 |
| 1 | 技术不可行或资源严重不足 |

**检查项**:
- 现有技术栈能否支撑
- Token/时间/人力成本是否可接受
- 外部依赖（兄弟项目/第三方工具）是否就绪

### 3. 一致性 (Consistency) — 权重 20%

| 得分 | 标准 |
|------|------|
| 5 | 与架构设计/编码规范/安全标准完全一致 |
| 4 | 基本一致，少量风格差异 |
| 3 | 主体一致，存在局部不一致 |
| 2 | 与现有标准有明显冲突 |
| 1 | 严重违反架构/规范 |

**检查项**:
- 与架构设计文档一致
- 与编码规范一致
- 与安全标准一致
- 与现有系统行为无冲突

### 4. 风险可控 (Risk) — 权重 15%

| 得分 | 标准 |
|------|------|
| 5 | 风险全面识别，每项高风险有详细应对方案+回退策略 |
| 4 | 风险识别充分，高风险有应对 |
| 3 | 主要风险已识别，部分应对措施不够详细 |
| 2 | 风险识别不充分，缺少应对方案 |
| 1 | 未进行风险分析 |

**检查项**:
- 至少识别 3 项风险（技术/集成/回退）
- 每项风险有应对措施
- 高风险有回退策略

### 5. 可测性 (Testability) — 权重 15%

| 得分 | 标准 |
|------|------|
| 5 | 验收标准量化明确，验证方法可执行 |
| 4 | 验收标准基本可量化 |
| 3 | 部分验收标准可量化 |
| 2 | 验收标准模糊，难以验证 |
| 1 | 无验收标准 |

**检查项**:
- 每项验收标准可量化
- 验证方法可执行
- 通过/失败标准明确

## 评分计算

```
加权总分 = sum(各维度得分 * 权重)
```

## Go/No-Go 决策规则

| 条件 | 决策 |
|------|------|
| 加权总分 >= 3.5 且所有高风险有应对 | **PASS** — 方案通过，进入执行 |
| 加权总分 2.5-3.5 或有高风险无应对 | **CONDITIONAL** — 有条件通过，需修订再审 |
| 加权总分 < 2.5 或关键需求未覆盖 | **REJECT** — 不通过，需重新设计 |

## 评审流程

1. **预审**: 自动化检查清单（6 项完整性检查）
2. **正式评审**: 五维评分 + 评审发现 + 风险登记
3. **结论**: PASS / CONDITIONAL / REJECT
4. **修订闭环**: CONDITIONAL 需逐条回应意见后再审
