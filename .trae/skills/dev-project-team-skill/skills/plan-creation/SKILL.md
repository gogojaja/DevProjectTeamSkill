# Plan Creation — 方案制定流程子技能

> 版本: v1.0 | 日期: 2026-09-06 | 对齐: IEEE 828 / PMBOK 规划过程组 / PRINCE2 阶段门禁

## 定位

通用方案制定流程，适用于项目级实施方案（实施方案/整改方案/迁移方案/扩展方案等）。
与 `best-practice-solution`（技术选型决策）互补：
- **技术选型/架构决策** → `best-practice-solution`
- **项目级实施方案** → `plan-creation`（本子技能）
- **域内方案**（测试方案/发布方案/架构方案）→ 对应角色包

## 触发条件

用户说「制定方案」「写方案」「实施方案」「方案评审」「执行计划」时加载。

## 8 步生命周期

```
Step 1: 需求采集与可行性评估    [必选]
    ↓  输出：可行性摘要
Step 2: 方案编写（含风险评估）  [必选]
    ↓  输出：方案草案 v0.x
Step 3: 预审 + 正式评审        [必选]
    ↓  输出：评审报告
Step 4: 修订闭环 + 基线化      [必选]
    ↓  输出：方案定稿 v1.0
Step 5: 执行计划分解（WBS）    [按需]
    ↓  输出：执行计划
Step 6: 执行 + 进度监控        [按需]
    ↓  输出：进展报告
Step 7: 变更控制              [条件触发]
    ↓  输出：变更请求
Step 8: 收尾复盘              [按需]
    ↓  输出：经验教训
```

### Step 1: 需求采集与可行性评估 [必选]

**输入**: 用户需求描述、项目上下文
**动作**:
1. 采集并澄清需求（至少确认范围/约束/验收标准）
2. 三维度可行性评估：
   - 技术可行性：现有技术栈能否实现？
   - 经济可行性：成本（token/时间/人力）是否可接受？
   - 操作可行性：是否影响现有运行系统？
3. 输出可行性摘要（1 段话 + 结论 GO/HOLD/KILL）

**输出**: 可行性摘要（嵌入方案文档第一章）

### Step 2: 方案编写（含风险评估）[必选]

**输入**: 可行性摘要、项目代码/文档
**动作**:
1. 按标准模板编写方案草案（见 `domain/plan_templates.md`）
2. 必须包含的章节：背景与目标 / 方案设计 / 变更清单 / 风险评估 / 验收标准
3. 风险至少识别 3 项（技术风险/集成风险/回退风险）
4. 标注版本号 v0.1（草案）

**输出**: 方案草案 v0.x

### Step 3: 预审 + 正式评审 [必选]

**预审**（自动化检查清单）:
- [ ] 需求覆盖：每个需求都有对应方案段落
- [ ] 风险识别：至少 3 项风险 + 应对措施
- [ ] 回退方案：是否有回退策略
- [ ] 验收标准：是否可量化验证
- [ ] 变更清单：是否列出所有变更文件
- [ ] 版本信息：版本号/日期/状态齐全

**正式评审**（五维评分，见 `domain/review_criteria.md`）:

| 维度 | 权重 | 评审要点 |
|------|------|---------|
| 完整性 | 25% | 需求全覆盖、场景无遗漏 |
| 可行性 | 25% | 技术可实现、资源充足 |
| 一致性 | 20% | 与架构/标准/约束一致 |
| 风险可控 | 15% | 风险已识别、应对充分 |
| 可测性 | 15% | 可验证、验收标准明确 |

**Go 条件**: 加权得分 >= 3.5 且所有高风险有应对方案

**输出**: 评审报告（五维评分 + 意见清单 + 结论 PASS/CONDITIONAL/REJECT）

### Step 4: 修订闭环 + 基线化 [必选]

**动作**:
1. 逐条回应评审意见（接受/部分接受/拒绝 + 理由）
2. 修订方案文档
3. 版本号升级为 v1.0（基线版）
4. 生成三份定稿文档：方案文档 + 执行计划 + 评审报告

**输出**: 方案定稿 v1.0 + 基线标记

### Step 5: 执行计划分解（WBS）[按需]

**触发**: 复杂方案（变更文件 >3 或有跨项目影响）
**动作**:
1. 将方案条目分解为可执行任务
2. 每个任务标注：负责角色 / 依赖 / 预估工时 / 检查点
3. 识别关键路径

**输出**: 执行计划（任务表格 + 里程碑）

### Step 6: 执行 + 进度监控 [按需]

**动作**:
1. 按执行计划逐步实施
2. 每完成一个 Phase 记录进展
3. 偏差检测：实际 vs 计划，偏差 >20% 触发预警

**输出**: 进展报告

### Step 7: 变更控制 [条件触发]

**触发**: 执行中需要偏离已基线化的方案
**动作**:
1. 填写变更请求（变更内容/原因/影响分析）
2. 评估对范围/进度/成本/质量的影响
3. 获批后修订基线

**输出**: 变更请求 + 影响分析

### Step 8: 收尾复盘 [按需]

**动作**（AAR 方法）:
1. 我们计划做什么？→ 回顾原始目标
2. 实际发生了什么？→ 对照事实
3. 为什么有差异？→ 根因分析
4. 下次该怎么做？→ 改进行动项

**输出**: 经验教训记录

## 阶段裁剪规则

见 `domain/workflow_rules.md`。简言之：
- **简单方案**（变更 <=3 文件 + 无跨项目影响）：Step 1-4 必选，Step 5-8 可跳过
- **标准方案**（变更 4-10 文件 或 单项目内）：Step 1-6 必选，Step 7-8 按需
- **复杂方案**（跨项目 或 变更 >10 文件）：Step 1-8 全部执行

## 与角色包协作

- 方案可由任何角色触发（需求/架构/开发/测试/投产）
- 评审统一经 `role-governance` 的 `stage_review` 执行
- 基线化统一经 `role-governance` 的 `solidify` 执行
- 变更控制统一经 `role-governance` 的 `change_audit` 记录

## 交付物标准

每次方案制定完成后，必须生成以下三份文档：

| 文档 | 内容 | 命名规则 |
|------|------|---------|
| 技术方案 | 背景/目标/方案/风险/变更清单 | `{方案名}方案.md` |
| 执行计划 | 分步执行表格 + 完成状态 | `{方案名}_执行计划.md` |
| 评审报告 | 五维评分 + 意见清单 + 结论 | `{方案名}_评审报告.md` |
