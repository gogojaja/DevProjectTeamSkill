# 架构决策评审详细内容参考（Architecture Review Details）

> 本文件为 `architecture-review-skill` 各环节**详细执行内容**的参考文档，按需加载。
> SKILL.md 各环节仅保留 Definition of Ready / Definition of Done / 规则，详细表格与本文件对应章节为准。

---

## 环节 1：架构决策记录细节

### 1.1 ADR 编写（MADR 格式）

每条架构决策独立编写一个 ADR 文件，采用 MADR（Markdown Architectural Decision Records）格式：

```markdown
# ADR-<编号>: <决策标题>

**日期**: YYYY-MM-DD
**状态**: Proposed | Accepted | Deprecated | Superseded by ADR-<n>
**决策者**: <姓名/团队>

## 上下文（Context）
描述迫使做出此决策的约束、问题、背景。
列出考虑过的备选方案。

## 决策（Decision）
最终选择的方案及理由。

## 选项（Options Considered）
### 方案 A: <名称>
- 优点: ...
- 缺点: ...
- 评分: ...

### 方案 B: <名称>
- 优点: ...
- 缺点: ...
- 评分: ...

## 驱动因素（Drivers）
- 质量属性优先级
- 约束条件
- 七原则合规要求

## 后果（Consequences）
- 正面后果: 此决策带来的收益
- 负面后果: 此决策的成本/限制
- 风险与缓解: 引入的风险及缓解措施
```

**ADR 编号规则**：
- `ADR-001` 至 `ADR-999`，按决策顺序编号
- 常见 ADR 类型：

| ADR 类型 | 示例 |
|----------|------|
| 技术栈选型 | ADR-001: 后端框架选型 Python Flask vs FastAPI |
| 架构模式决策 | ADR-002: 单体 vs 微服务架构 |
| 数据库选型 | ADR-003: 关系型 vs NoSQL |
| 通信协议 | ADR-004: REST vs gRPC vs GraphQL |
| 缓存策略 | ADR-005: 本地缓存 vs 分布式缓存 |
| 安全方案 | ADR-006: 认证方案 OAuth2 vs JWT |
| 部署策略 | ADR-007: 容器化 vs 虚拟机 |

### 1.2 ATAM 权衡分析

对涉及质量属性权衡的关键决策执行 ATAM 分析：

| 步骤 | 内容 |
|------|------|
| ① 呈现场景 | 收集质量属性场景（刺激-响应-度量） |
| ② 架构分析 | 分析架构方案对场景的支持度 |
| ③ 识别敏感点 | 影响质量属性的架构决策点 |
| ④ 识别权衡点 | 同时影响多个质量属性的决策点 |
| ⑤ 识别风险 | 架构设计中的风险点 |
| ⑥ 生成报告 | ATAM 权衡分析报告 |

**典型权衡场景**：

| 权衡对 | 示例 |
|--------|------|
| 性能 vs 安全 | 是否加密所有传输（加密增加延迟） |
| 便捷 vs 灵活 | 是否使用 ORM（便捷但灵活性降低） |
| 跨平台 vs 性能 | 是否使用容器化（跨平台但性能开销） |
| 成熟 vs 创新 | 是否使用新技术（创新但风险高） |

### 1.3 技术选型决策矩阵

| 候选方案 | 成熟度(20%) | 稳定性(15%) | 安全性(15%) | 性能(10%) | 生态(10%) | 跨平台(10%) | 可移植(10%) | 学习(5%) | 运维(5%) | 加权总分 |
|----------|-------------|-------------|-------------|-----------|-----------|-------------|-------------|-----------|-----------|----------|
| 方案A | 5 | 4 | 4 | 5 | 4 | 5 | 4 | 4 | 4 | 4.35 |
| 方案B | 4 | 5 | 5 | 4 | 5 | 4 | 5 | 3 | 5 | 4.40 |
| 方案C | 3 | 3 | 3 | 3 | 3 | 3 | 3 | 5 | 3 | 3.10 |

### 1.4 架构决策评审
关键架构决策（影响核心质量属性的）需架构委员会/技术委员会评审。

## 环节 2：架构原型验证细节

### 2.1 POC 方案设计

| 设计项 | 内容 |
|--------|------|
| 验证目标 | 识别的关键技术风险点列表 |
| 验证范围 | 需要验证的技术点（框架/中间件/集成/性能） |
| 验证方法 | Spike（技术探针）/ 小规模原型 / 基准测试 |
| 成功标准 | 每个验证点的量化通过标准 |
| 时间盒 | 每个验证点的时间限制（通常 1-3 天） |

### 2.2 关键技术验证（Spike）

| 验证类型 | 验证内容 | 验证方法 |
|----------|----------|----------|
| 框架验证 | 核心框架是否满足功能/性能需求 | 编写最小可用原型 |
| 中间件验证 | 消息队列/缓存/数据库是否满足要求 | 基准测试 |
| 集成验证 | 外部系统集成是否可行 | 接口联调测试 |
| 性能验证 | 关键路径性能是否达标 | 压力测试 |
| 安全验证 | 安全方案是否有效 | 漏洞扫描 + 渗透预检 |

### 2.3 跨平台兼容性验证

| 验证项 | 验证内容 | 通过标准 |
|--------|----------|----------|
| 多平台部署 | 在目标平台（Linux/Windows/Docker/K8s）部署测试 | 全部目标平台可部署 |
| 厂商锁定检测 | 检测是否依赖特定厂商的专有技术 | 无厂商锁定或锁成本可控 |
| 平台差异抽象 | 平台抽象层是否有效隔离差异 | 业务代码无平台判断逻辑 |
| 配置外部化验证 | 配置是否完全外部化（环境变量/配置文件） | 代码中无硬编码配置 |

### 2.4 性能基准测试

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 响应时间 | 关键接口 P50/P95/P99 | P99 <= 200ms |
| 吞吐量 | 每秒处理请求数 (TPS) | >= 1000 TPS |
| 资源利用率 | CPU/内存/磁盘/网络 | CPU < 70%, 内存 < 80% |
| 并发能力 | 最大并发用户数 | >= 目标并发数 |
| 错误率 | 请求错误率 | < 0.1% |

### 2.5 安全验证

| 验证项 | 验证方法 |
|--------|----------|
| 漏洞扫描 | SAST（静态扫描）+ DAST（动态扫描） |
| 渗透预检 | OWASP Top 10 检查 |
| 认证授权验证 | 权限模型有效性验证 |
| 数据加密验证 | 传输/存储加密有效性验证 |

### 2.6 七原则验证

| 原则 | 验证方法 | 通过标准 |
|------|----------|----------|
| 成熟性 | 技术栈在生产环境案例验证 | 有可验证的生产案例 |
| 稳定性 | 故障注入/混沌测试 | 单点故障不影响整体 |
| 安全性 | 漏洞扫描 + 渗透预检 | 无高危漏洞 |
| 高效性 | 性能基准测试 | 性能指标达标 |
| 便捷性 | 新人上手测试 | 新人可在 2 天内理解架构 |
| 跨平台性 | 多平台部署测试 | 全部目标平台可部署 |
| 可移植性 | 环境切换测试 | 切换成本 <= 1 人天 |

## 环节 3：架构评审细节

### 3.1 ATAM 评估

| 步骤 | 内容 | 产出 |
|------|------|------|
| ① 场景收集 | 从相关方收集质量属性场景（刺激-响应-度量） | 质量属性场景清单 |
| ② 架构分析 | 分析架构对每个场景的支持度 | 场景-架构映射表 |
| ③ 敏感点识别 | 识别影响质量属性的架构决策点 | 敏感点清单 |
| ④ 权衡点识别 | 识别同时影响多个质量属性的决策点 | 权衡点清单 |
| ⑤ 风险识别 | 识别架构中的风险点 | 风险清单（写入风险台账） |
| ⑥ 评估报告 | 生成 ATAM 评估报告 | ATAM 评估报告 |

### 3.2 架构评审检查清单（15 类检查项）

| 序号 | 检查类别 | 检查项 |
|------|----------|--------|
| 1 | 分层架构 | 分层是否清晰？职责边界是否明确？ |
| 2 | 模块耦合 | 模块间耦合度是否合理？有无循环依赖？ |
| 3 | 模块内聚 | 模块内聚度是否高？是否单一职责？ |
| 4 | 接口设计 | 接口是否标准化？版本管理是否规范？ |
| 5 | 数据架构 | 数据模型是否合理？存储策略是否适当？ |
| 6 | 安全架构 | STRIDE 是否全覆盖？纵深防御是否到位？ |
| 7 | 性能设计 | 性能预算是否合理？瓶颈是否识别？ |
| 8 | 可扩展性 | 是否支持水平扩展？扩展点是否预留？ |
| 9 | 可观测性 | 日志/指标/追踪是否覆盖？告警是否配置？ |
| 10 | 容错设计 | 故障隔离/降级/熔断/重试是否设计？ |
| 11 | 跨平台性 | 平台差异是否抽象？厂商锁定是否避免？ |
| 12 | 可移植性 | 配置外部化/无状态化/12-Factor 是否合规？ |
| 13 | 技术选型 | 是否成熟稳定？是否符合七原则？ |
| 14 | 文档完整性 | 4+1 视图/C4/ADR/组件/接口文档是否齐全？ |
| 15 | 需求覆盖 | 架构是否覆盖 SRS 全部需求？追溯是否完整？ |

### 3.3 架构反模式检查

| 反模式 | 描述 | 检查方法 |
|--------|------|----------|
| God Object | 单个组件承担过多职责 | 检查组件职责数量 |
| Spaghetti Architecture | 架构层次混乱，依赖无序 | 检查依赖图方向性 |
| Big Ball of Mud | 无明确架构，代码混杂 | 检查分层和模块化 |
| Vendor Lock-in | 深度依赖特定厂商技术 | 检查厂商专有 API 使用 |
| Gold Plating | 过度设计，超出需求 | 检查是否有不必要的复杂度 |
| Not Invented Here | 拒绝使用成熟第三方方案 | 检查自研 vs 复用决策 |
| Architecture by Implication | 隐式架构，无显式设计 | 检查架构文档完整性 |
| Hot Potato | 问题传递而非解决 | 检查异常处理和职责边界 |

### 3.4 质量属性场景验证

每个质量属性编写场景并验证：
```
场景格式：[刺激源] [刺激] [制品] [环境] [响应] [响应度量]
示例：[用户] [发起 1000 并发请求] [Web 服务] [正常负载] [响应时间] [P99 <= 200ms]
```

### 3.5 七原则终审

| 原则 | 终审内容 | 判定标准 |
|------|----------|----------|
| 成熟性 | 技术栈最终确认 LTS 版本 + 生产案例 | 有佐证 |
| 稳定性 | 可用性指标 + 容错设计终审 | 达标 |
| 安全性 | 安全架构 + 验证结果终审 | 无高危 |
| 高效性 | 性能基准 + 优化方案终审 | 达标 |
| 便捷性 | 可维护性 + 可观测性终审 | 达标 |
| 跨平台性 | 多平台部署 + 厂商锁定检测终审 | 通过 |
| 可移植性 | 环境切换 + 12-Factor 合规终审 | 通过 |

### 3.6 对接 ProjectMonitorSkill

调用 ProjectMonitorSkill 执行 `action=stage_review` 架构专项评审：
- 五维度自动校验：范围合规、功能逻辑质量、工程规范、风险安全、范围跟踪检查
- 输出评审报告 Excel（5 Sheet）：评审摘要、缺陷清单、逐原则评审详情、范围跟踪比对表、角色权限分布总览

## 环节 4：架构基线固化细节

### 4.1 架构设计说明书定稿

整合全部架构设计文档，形成完整的《架构设计说明书》：

| 章节 | 内容 |
|------|------|
| 1. 引言 | 文档目的、范围、术语、参考资料 |
| 2. 架构策略 | 业务上下文、驱动因素、质量属性、技术选型 |
| 3. 4+1 视图 | 逻辑视图、进程视图、开发视图、物理视图、场景视图 |
| 4. C4 模型 | 系统上下文图、容器视图、组件视图、代码结构 |
| 5. 组件设计 | 组件职责、接口、依赖、通信、生命周期 |
| 6. 接口设计 | API 契约、版本管理、错误码、认证、限流 |
| 7. 数据架构 | ER 模型、数据字典、存储策略、数据流转 |
| 8. 安全架构 | STRIDE 建模、认证授权、数据安全、审计链 |
| 9. 架构决策 | ADR 汇总、ATAM 权衡分析 |
| 10. 原型验证 | POC 报告、性能基准、安全验证 |
| 11. 七原则合规 | 七原则检查表、验证结果 |
| 12. 开发指南 | 编码规范、目录结构、依赖管理、环境搭建 |

### 4.2 ADR 归档
全部 ADR 统一编号归档，生成 ADR 归档清单。

### 4.3 开发指南输出

| 内容 | 说明 |
|------|------|
| 编码规范 | 语言/框架编码标准 |
| 目录结构 | 项目目录/包结构规范 |
| 依赖管理 | 第三方依赖版本锁定、依赖管理策略 |
| 开发环境搭建 | 环境配置、工具链、调试指南 |
| 开发流程 | 分支策略、Code Review、CI/CD |

### 4.4 架构资产清单
生成全部架构产出物清单（含文件名、版本号、固化时间），写入 ProjectMonitorSkill「范围跟踪台账」Sheet。

### 4.5 架构追溯矩阵建立

建立需求→架构元素→组件的双向追溯矩阵：

| 需求编号 | 架构元素 | 组件 | 接口 | 设计文档章节 | ADR |
|----------|----------|------|------|-------------|-----|
| REQ-FUNC-XXX | 认证模块 | AuthService | /api/auth | §5.1, §6.1 | ADR-006 |
| REQ-NFR-XXX | 性能优化 | CacheManager | — | §7.3 | ADR-005 |

写入 ProjectMonitorSkill 主台账新增「架构追溯矩阵」Sheet。

### 4.6 对接 ProjectMonitorSkill

调用 ProjectMonitorSkill 执行：
- `check_gate`：架构阶段门禁校验（含架构阶段专项门禁校验）
- `stage_close`：架构基线固化（备份 + 更新版本 + 产出物清单）

## 5. 架构变更分析细节（change_analysis）

### 5.1 七维度影响评估

| 维度 | 评估内容 |
|------|----------|
| 架构模式影响 | 是否改变整体架构模式（如单体→微服务） |
| 组件影响 | 受影响的组件列表、依赖关系变更 |
| 接口影响 | 受影响的接口契约、版本兼容性 |
| 数据影响 | 数据模型变更、迁移影响 |
| 安全影响 | 安全架构变更、威胁模型更新 |
| 性能影响 | 性能基准变化、资源需求变更 |
| 七原则影响 | 对七大设计原则的影响评估 |

### 5.2 变更流程

```
提出架构变更 → 七维度影响评估 → ProjectMonitorSkill change_audit → 用户审批 → 
更新架构设计 → 更新 ADR → 重新评审受影响部分 → 更新追溯矩阵 → 重新固化基线
```
