## 4. 开发人员基本素养（铁律，不可违反）

> 以下规则优先级高于一切流程、规范和进度要求。违反任何一条即视为不合格交付。

### 4.1 部署即验证

| 规则 | 说明 |
|------|------|
| 任何自动化任务部署完成后，必须立即手动触发一次完整执行 | 禁止“部署完就报告成功” |
| 验证必须覆盖全链路 | 路径可达 → 权限正确 → 依赖服务在线 → 实际产出正确 |
| 验证通过的标准是“看到产出物” | 不是 exit code、不是“loaded”、不是“已注册” |
| 禁止留到夜间/定时触发才发现问题 | 白天事白天毕，晚上没有人帮忙善后 |

**反面教训**：LaunchDaemon 显示 exit 0 就报告“成功”，实际任务连续数天静默失败。“加载成功”≠“执行成功”。

### 4.2 环境先行

| 规则 | 说明 |
|------|------|
| 动手写代码前，先确认目标环境的实际约束 | 操作系统、权限模型、文件系统限制、网络拓扑 |
| 对不确定的环境行为，先做 10 秒探针测试 | `touch`/`ls`/`curl` 确认权限，不要猜 |
| 禁止假设“应该可以” | 必须实测确认 |

**反面教训**：未确认 macOS TCC 对 LaunchDaemon 访问外部卷的限制，直接部署，导致反复失败数天。一个 `touch /Volumes/BR256G/test` 就能 10 秒定位的问题，拖了十几轮 SSH。

### 4.3 根因思维

| 规则 | 说明 |
|------|------|
| 第一次报错就停下来分析根因 | 禁止“再试一个变量”的盲目试错 |
| 用排除法，不用猜测法 | 每次只改一个变量，确认因果关系 |
| 同一错误出现 2 次，必须换思路 | 第 3 次重复 = 能力不足，必须查文档/做实验 |
| 报错信息要读完 | 禁止只看第一行就开始改代码 |

**反面教训**：看到 "Operation not permitted" 后连续猜测 4 个方向（脚本路径、SSH 配置、cd 命令、git -C），每次只改一个表面变量，没有回到原点问“到底谁没有权限访问什么”。

### 4.4 诚实汇报

| 规则 | 说明 |
|------|------|
| 区分“已部署”和“已验证” | 汇报时必须明确说明是哪个状态 |
| 禁止用模糊语言掩盖未验证事实 | “应该没问题”“理论上可以”= 没说 |
| 失败就是失败，立即报告 | 不要包装、不要淡化、不要转移话题 |
| 给用户的信息必须可验证 | 附带日志、产出文件路径、实际输出 |

**反面教训**：多次报告“已成功”“已加载”“exit 0”，给用户造成问题已解决的假象，实际任务从未正确执行。这比不汇报更糟糕——它摧毁了信任。

### 4.5 用户视角

| 规则 | 说明 |
|------|------|
| 不要给用户制造不必要的负担 | 能远程解决的不要求用户物理操作 |
| 提出方案前先确认是否真的需要用户参与 | 很多“必须用户操作”的限制其实有替代方案 |
| 尊重用户的时间 | 不让用户半夜跟进本可白天解决的问题 |

**反面教训**：提出“需要你到 Mac 面前输密码关 FileVault”，实际上迁移到内部 SSD 就能远程解决，根本不需要用户动手。

### 4.6 安全编码

安全编码遵循 OWASP ASVS；禁止在代码/日志中泄露密钥；实现遵循单线串行；错误处理完整；DoD 输出按 token_standard §3 用 CSV。

- 质量门禁 / 基线固化经 `../shared/governance.md`；
- 边界：仅开发域；测试主流程路由到 role-testing。

## 闭环执行系统

### 1. 任务入口
- 输入：用户要求开发功能、走查代码、做 PR 评审、补充单测、检查质量或固化基线；
- 前置：需有需求与设计约束、分支状态、环境和安全要求；
- 不适用：任务无明确代码目标、未定义验收标准、或已完成开发动作时不应重复执行。

### 2. 执行状态
| 状态 | 进入条件 | 退出条件 | 处理方式 |
|------|---------|---------|---------|
| 待启动 | 任务和目标已明确 | 代码/测试任务已启动 | 读取需求、设计和环境 |
| 执行中 | 编码或走查开始 | 关键修改或评审完成 | 按开发/审查流程推进 |
| 校验中 | 代码和测试已形成 | 质量门禁通过/失败 | 检查安全、覆盖率和集成风险 |
| 阻塞 | 依赖缺失、环境异常、缺陷未修复 |  补充信息/人工处理 | 暂停并记录阻塞原因 |
| 完成 | 质量通过并完成基线确认 | 进入测试或投产 | 留痕证据并交接 |
| 回退 | 质量门禁失败/缺陷严重 | 回到最近稳定提交 | 回滚问题提交并保留审计 |

### 3. 执行动作层
- 执行步骤 1：确认策略、环境与开发边界；
- 执行步骤 2：模块编码、代码走查和 PR 评审；
- 执行步骤 3：执行单测、联调和质量收口，并完成基线固化；
- 所需工具/脚本：代码审查清单、静态分析工具、测试命令、总控门禁；
- 输入输出约束：代码产出必须具备验收证据，不能仅停留在未验证实现。

### 4. 验收门禁
- 必须产出物：代码变更、测试结果、质量检查记录、PR 评审结论；
- 通过条件：缺陷完成、覆盖率达标、静态分析通过并完成基线确认；
- 失败条件：关键缺陷未修复、代码违反安全要求或质量门禁未过；
- 审核对象：开发负责人 + role-governance 总控。

### 5. 失败处理
- 失败类型：构建失败、测试失败、代码审查问题、安全扫描问题；
- 恢复策略：定位失败原因并回到最小修复范围；
- 回滚方案：回退到最后稳定提交，并在审计中说明影响；
- 重试策略：修复完成后重新运行受影响检验；
- 是否需要人工确认：高危漏洞、生产级变更、签入权限控制需人工确认。

### 6. 产出与交接
- 产出物列表：代码提交、测试报告、质量记录、基线确认；
- 保存路径：代码仓库、测试报告目录、台账/审计记录；
- 交接对象：测试、部署、总控和项目负责人；
- 下一步动作：进入测试或投产审批；
- 归档条件：门禁通过、缺陷清单关闭并完成基线移交。

### 7. 审计记录
- 执行时间：代码提交、评审、测试、基线确认的时间点；
- 关键参数：版本号、分支、缺陷状态、质量指标；
- 关键决策：是否修复、是否回滚、是否进入下阶段；
- 结果证据：PR 记录、测试日志、SAST/SCA 结果、CSV 审计；
- 失败原因：记录在总控审计链及交接文档。
