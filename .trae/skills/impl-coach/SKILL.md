# impl-coach 架构实现指导技能

> 版权：`../shared/references/COPYRIGHT.md` Token：`../shared/references/token_standard.md`
> 上游依赖：`role-architecture`（架构视图与 ADR）· `role-development`（编码规范与铁律）

## 1. 元数据

- **技能版本**：v1.0.0 **发布日期**：2026-09-07
- **变更记录**：
  - v1.0.0：初始版本，填补架构设计到代码实现之间的指导空白
- **参考标准**：ISO/IEC/IEEE 42010（架构描述）· GoF 设计模式 · Clean Architecture · SOLID · ADR（Michael Nygard）
- **定位**：编码实操桥梁层——不替代 `role-architecture`（架构设计）和 `role-development`（编码管理），专注**从架构到代码的翻译与落地**

## 2. 触发规则

用户表达「根据架构写代码/模块怎么实现/用什么设计模式/ADR 怎么落地/帮我搭模块骨架/分层怎么映射/接口怎么设计/代码结构怎么组织」时加载本技能。先 Read 路由表，命中后只读对应 `domain/*.md`。

## 3. 与现有技能的边界

| 技能 | 职责 | 本技能不重复 |
|------|------|-------------|
| `role-architecture` | 产出架构视图、ADR、C4 模型 | 本技能**消费**架构产物，不重新设计架构 |
| `role-development` / coding.md | 编码规范、安全编码规则、铁律 | 本技能**遵循**编码规则，不重新定义规范 |
| **impl-coach（本技能）** | **翻译层**：架构 → 代码结构、模式选型、模块骨架、ADR 落地 | 独有职责 |

## 4. 流程（路由到 domain/）

| 环节 | action | 明细 |
|------|--------|------|
| 架构解读 | interpret_architecture | `domain/architecture-to-code.md`（C4/分层 → 代码映射） |
| 模式选型 | select_pattern | `domain/pattern-selection.md`（GoF / 架构模式 / 场景匹配） |
| ADR 落地 | implement_adr | `domain/adr-to-code.md`（ADR 决策 → 代码约束与结构） |
| 模块骨架 | scaffold_module | `domain/module-scaffold.md`（目录/文件/接口模板） |
| 接口实现 | implement_contract | `domain/architecture-to-code.md`（契约 → 接口代码） |
| 实现评审 | review_implementation | `domain/pattern-selection.md`（模式合规性与反模式检查） |

## 5. 核心原则

1. **架构驱动代码**：代码结构必须反映架构决策，而非随意组织
2. **模式服务于场景**：设计模式是工具而非目标，按场景选型而非预设
3. **ADR 可追溯**：每个关键代码结构都能追溯到对应的 ADR 或架构约束
4. **骨架即可编译**：输出的模块骨架必须是可编译/可运行的最小结构
5. **约定优于配置**：优先使用团队已约定的命名、目录和分层规范

## 6. 输出规范

- 实现方案 / 模式选型记录 / 模块骨架 按 token_standard §3 输出 CSV 摘要
- 代码骨架遵循项目已有目录规范（`../shared/references/directory_structure.md`）
- 边界：仅实现指导域；不产出架构设计（归 role-architecture）、不产出编码规范（归 role-development）

## 闭环执行系统

### 1. 任务入口
- 输入：用户要求根据架构设计实现模块、选型设计模式、落地 ADR、生成模块骨架；
- 前置：需有架构视图（C4/分层图）或 ADR 文档、编码规范（来自 role-development）；
- 不适用：无架构约束的脚本/一次性代码、纯架构设计（无编码目标）。

### 2. 执行状态
| 状态 | 进入条件 | 退出条件 | 处理方式 |
|------|---------|---------|---------|
| 待启动 | 架构产物与编码目标已明确 | 实现方案已制定 | 读取架构视图与 ADR |
| 执行中 | 开始翻译架构为代码结构 | 模块骨架/模式选型完成 | 按 domain 明细逐步实现 |
| 校验中 | 代码骨架已形成 | 实现评审通过 | 检查模式合规与架构一致性 |
| 阻塞 | 架构信息不足或 ADR 缺失 | 补充架构输入 | 暂停并列出缺失信息清单 |
| 完成 | 模块骨架可编译且模式合规 | 交付给 role-development 编码 | 输出实现方案与骨架代码 |
| 回退 | 实现与架构严重不一致 | 回到最近合规结构 | 记录偏差并重构 |

### 3. 执行动作层
- 执行步骤 1：解读架构视图，提取组件边界、依赖方向与接口契约；
- 执行步骤 2：按场景选型设计模式，记录选型理由；
- 执行步骤 3：将 ADR 决策翻译为代码结构约束；
- 执行步骤 4：生成模块骨架（目录、文件、接口、桩代码）；
- 所需输入：C4 模型 / 架构图 / ADR 文档 / 编码规范；
- 输入输出约束：骨架必须可编译，模式选型必须有理由，ADR 必须有追溯。

### 4. 验收门禁
- 必须产出物：实现方案、模块骨架代码、模式选型记录、ADR 追溯映射；
- 通过条件：骨架可编译、依赖方向符合架构、模式选型有理由、ADR 100% 可追溯；
- 失败条件：骨架不可编译、依赖方向违反架构、ADR 无对应代码映射；
- 审核对象：开发负责人 + 架构负责人。

### 5. 失败处理
- 失败类型：架构信息不足、模式选型冲突、骨架编译失败；
- 恢复策略：补充架构输入或回退到上一合规结构；
- 是否需要人工确认：架构偏差与模式冲突需人工仲裁。

### 6. 产出与交接
- 产出物列表：实现方案文档、模块骨架代码、模式选型记录、ADR→代码映射表；
- 交接对象：role-development（进入编码实现）、role-architecture（架构一致性确认）；
- 下一步动作：进入 role-development 编码实现与代码审查。

### 7. 审计记录
- 执行时间：架构解读、模式选型、骨架生成的时间点；
- 关键参数：架构版本、ADR 编号、模式名称、模块清单；
- 关键决策：模式选型理由、ADR 落地方案、分层映射决策；
- 结果证据：实现方案文档、骨架代码提交、模式选型 CSV。
