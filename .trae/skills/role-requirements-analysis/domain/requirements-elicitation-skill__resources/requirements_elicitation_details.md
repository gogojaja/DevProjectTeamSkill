| 项目 | 内容 |
|------|------|
| 需求工作目录 | 项目根 `requirements/` 目录创建 |

## 环节 2：需求收集（gather_requirements）

### 2.1 需求来源识别

| 来源类型 | 示例 | 说明 |
|----------|------|------|
| 业务方 | 产品经理、业务部门、最终用户 | 核心需求来源 |
| 访谈 | 干系人访谈、焦点小组 | 挖掘隐性需求 |
| 现有系统 | 遗留系统、竞品分析 | 功能/数据迁移来源 |
| 合规 | 法规、行业标准、安全规范 | 强制需求来源 |
| 技术约束 | 平台、基础设施、第三方依赖 | 技术边界来源 |

### 2.2 结构化登记

登记至 `需求收集清单_<对象>_<版本>_v2.csv`：

| 字段 | 内容 |
|------|------|
| 需求编号 | 规则编号（如 REQ-ORG-01 / REQ-RB-01，按 §2.6 来源载体前缀） |
| 来源载体 | 来源载体编码（RB/RD/ORG/PRJ/FLOW/TODO，见 §2.6） |
| 原子行为描述 | EARS 风格行为化描述：`[条件/触发]+[角色]+动作+对象+数据范围`（见 §2.4） |
| MoSCoW | 优先级（Must/Should/Could/Won't） |
| 分类 | 初步分类（功能/非功能/接口/界面/安全/数据/环境） |
| 验收标准 | 可量化、可测试的验收条件（INVEST·Testable） |
| 约束依据 | 派生需求所依据的合规约束/基本原则编号（无则「—」） |
| 状态 | 待评审/已评审/已实现/范围外 |

### 2.3 来源追溯

来源追溯写入「来源映射」区：来源载体 → 来源名称 → 来源类型 → 关联需求编号 → 收集日期。

### 2.4 原子化提炼模板（EARS 风格）

**核心规则：来源载体 ≠ 需求条目。** 页签/原则/定义/矩阵均为**来源**，须提炼成可独立验收的原子需求；原则性描述、纯角色定义、流程说明不作为待实现需求条目。

- **合宜**：`REQ-ORG-01 项目管理员可对通知公告新增/编辑/删除，数据范围=全部项目；验收：新增后对目标用户即时可见，删除后不可见。`
- **不合宜**：`角色：项目管理员`（纯定义行）；`遵循保密性原则`（约束冒充需求）。

提炼要点（INVEST × 单一职责）：
1. 一条需求 = 一个可独立验收的原子行为（不整菜单/整矩阵做一条）；
2. 每条含「验收标准」列，能写出量化验收条件（IEEE 830 / ISO 29148:2018 §Testable）；
3. 行为化表达优先：`系统应支持〔角色〕对〔对象〕执行〔动作〕，数据范围〔X〕`。

### 2.5 字段与优先级强制项

- 清单必含列：需求编号｜来源载体｜原子行为描述｜MoSCoW｜分类｜验收标准｜约束依据｜状态；
- 条目必须标注 MoSCoW 优先级，不得空缺；
- 基本原则（R-RB-xx）并入「合规约束区」单独列出，**不作为需求条目**；其派生需求回标 `约束依据`；
- 角色定义/权限矩阵/流程类内容降级为「来源」，由收集人提炼为原子需求后登记，原表不直接进清单。

### 2.6 来源载体编码

| 编码 | 来源载体 | 示例 |
|------|----------|------|
| RB | 基本原则/合规约束 | 保密性原则、审计要求 |
| RD | 角色定义/权限矩阵 | 角色清单、模块级权限 |
| ORG | 组织级需求 | 组织流程/制度要求 |
| PRJ | 项目级需求 | 项目范围/业务目标 |
| FLOW | 流程类（已实现） | 既有流程说明，不纳入待实现清单 |
| TODO | 其他待定来源 | 待确认来源材料 |

### 2.7 收集盲区校验

对照七维度清单（func/sec/data/env 必选，nfr/if/ui 可选）校验收集盲区，输出《需求收集完整性检查表》，识别未覆盖维度。

## 环节 3：收集阶段刹车规则

1. **矛盾仲裁**：同一来源 3 次以上矛盾描述 → 暂停收集，业务方仲裁；
2. **范围控制**：需求超范围 → 标记「范围外」转 ProjectMonitorSkill `change_audit` 变更审计。
